# Leçons et erreurs à ne pas reproduire — checklist vivante

Document de travail, à consulter **avant** de commencer tout nouveau chantier ou module, et à enrichir chaque fois qu'une erreur, une régression, ou une incompréhension se répète d'un module à l'autre. Créé le 2026-08-24 à la demande de Denis, qui a remarqué que certaines erreurs corrigées un mois donné réapparaissaient dans un module suivant.

But : moins de temps perdu à corriger deux fois la même chose, une meilleure compréhension mutuelle entre Denis et l'assistant qui code, une cohérence réelle entre tous les modules de l'application.

**Règle d'usage** : avant de concevoir ou coder un nouveau module, relire cette liste. Dès qu'une nouvelle erreur récurrente ou un malentendu est identifié, l'ajouter ici tout de suite, avec la date.

**Voir aussi `docs/TACHES_VALIDEES.md`** : suivi commun à toute IA du dépôt des tâches de code validées avec Denis, avec un système `[CLOS]`/`[À FAIRE]` pensé pour éviter de relire ou re-vérifier ce qui est déjà fait (voir la Règle 8 de la section 10 ci-dessous, sur laquelle ce système s'appuie directement).

## 0bis. Qualité du français écrit - règle non négociable, à lire en premier

**Rencontré le 2026-08-27** : toute la maquette "Porte d'entrée" (des dizaines de textes visibles, titres, boutons, messages) avait été rédigée sans un seul accent - y compris des phrases recopiées mot pour mot depuis le vrai texte déjà validé de l'application (ex. le texte de Confidentialité). Cause identifiée : un réflexe de prudence légitime pour UN cas précis (éviter la corruption de caractères spéciaux constatée sur des tracés SVG récupérés via un outil - voir la section 9.19 ci-dessous) s'est généralisé par erreur à tout le texte de la maquette, sans jamais être corrigé ni même remarqué avant que Denis ne le signale. Denis a été explicite sur la gravité : "j'ai cru qu'on allait faire quelque chose de grave" et un rappel fort - une seule faute visible, pour un professionnel qui utilise l'IA, fait tomber la crédibilité de toute la conception à zéro.

**Règle, sans exception, à vérifier à chaque écrit, correction, édition, création de page** : toujours en français, orthographe et grammaire correctes, **tous les accents présents** (é, è, ê, à, ù, ô, ç, œ...), vocabulaire professionnel mais accessible au public cible de l'application (fragilité numérique, confiance en soi fragile), formulation sans ambiguïté. Aucune tolérance, même dans une maquette de travail, même dans un commentaire de code, même dans un contenu "provisoire" - un texte non accentué n'est jamais un raccourci acceptable, quelle qu'en soit la raison technique invoquée. Avant de considérer un texte terminé, le relire spécifiquement pour les accents manquants, surtout si une partie du code (regex, normalisation, contournement d'un bug d'encodage) a nécessité de manipuler du texte en ASCII à un moment - ce risque de contamination doit rester strictement localisé au code technique concerné, jamais s'étendre au texte visible.

**Ajout 2026-08-29** : des chaînes visibles sans accents peuvent déjà traîner dans le code, surtout dans les branches d'état vide / d'erreur / de repli, moins souvent relues. Exemple corrigé ce jour : `« Aucun resultat pour ... »` dans le rendu de la barre de recherche de l'accueil (`rendreResultatsRechercheERIP`). **Réflexe** : dès qu'on croise une de ces chaînes en travaillant à côté, la corriger (accents + guillemets français `« »`), comme pour le tiret long.

**Précision ajoutée le 2026-08-27, à la demande explicite de Denis** : cette exigence vaut **identiquement pour une maquette de travail que pour une vraie page de l'application** - pas de rigueur "allégée" sous prétexte que ce n'est "qu'une maquette". Raison donnée par Denis : le texte d'une maquette est souvent recopié tel quel dans le vrai code une fois validé ("on va l'acter comme étant définitif") - un raccourci pris "pour aller plus vite" sur une maquette peut donc se retrouver directement en production, sans jamais être revu. Aucune différence de standard entre les deux.

## 1. Cohérence visuelle et ergonomie

- **Des boutons, jamais des lignes de texte cliquables.** Plus lisible, plus beau, plus clair pour un public peu à l'aise avec l'informatique. **Attention : la classe Bootstrap `btn-link` viole cette règle même si l'élément est un vrai `<button>`** - visuellement, elle ressemble exactement à un lien texte souligné, ce qui trompe l'oeil malgré la balise correcte. Rencontré à nouveau le 2026-08-25 (Cohérence transversale, boutons "Passer cette étape"/"Annuler et choisir un fichier"). Toujours utiliser un style bordé/rempli (`btn-outline-secondary`, `btn-secondary`...), jamais `btn-link`, pour un bouton d'action - même petit, même secondaire.
  - **Autre variante du même piège, rencontrée le 2026-08-25 (module Repères)** : un vrai `<button>`, avec une classe CSS PERSONNALISÉE (`.reperes-picker-annuler`, `.reperes-lien-tout`) qui n'avait en réalité AUCUNE règle CSS écrite nulle part - le bouton hérite alors du style par défaut du navigateur ou d'un reset global de l'app, qui peut aussi bien ressembler à un lien texte que `btn-link`. **Après avoir créé une classe CSS dédiée pour un bouton, vérifier qu'une règle CSS existe réellement pour cette classe** (grep le nom de la classe dans `css/style.css`) - une classe non stylée est un piège aussi silencieux qu'une mauvaise classe Bootstrap.
- **Couleur cohérente selon le type d'élément**, sur tous les écrans de l'application : une recommandation (à lire/décider) et une action de correction (à appliquer concrètement) ne doivent pas se confondre visuellement - garder la même logique de couleur partout, pas une couleur différente réinventée à chaque nouvel écran.
- **Palette de référence à réutiliser partout** (déjà construite dans le Bilan, `BILAN_COULEURS_STATUT_PREPARATION`, `js/app.js`) : vert = point fort/bien démontré/aligné, ambre = absence/manque/à enrichir (pas une erreur, juste un vide), rouge = incohérence/contradiction/duplication gênante. Toujours via les variables CSS déjà prévues (`--success-*`, `--danger-*`...), jamais des teintes fixes en dur - ces variables s'adaptent déjà au mode sombre ET au daltonisme (voir commentaire dans le code, `js/app.js` ~ligne 12306). Ne jamais réinventer une nouvelle palette pour un nouveau module : reprendre celle-ci telle quelle.
- **Texte des boutons court, clair, cohérent d'un écran à l'autre** - éviter qu'un même type d'action porte un intitulé différent selon l'écran où on se trouve.
- Avant de livrer un nouvel écran, le comparer visuellement aux écrans déjà existants du même type (fenêtre ERIP, panneau, rapport...) pour vérifier qu'il n'invente pas silencieusement une nouvelle convention.
- **Raccourci de dictée vocale : toujours `Windows + H`, en gras d'un bloc, insécable.** Rencontré le 2026-08-31 : 8 emplacements de l'app le mentionnaient sous des formes mélangées (« Win + H », « touches Windows et H »), avec un gras incohérent. Convention fixée par Denis : tout texte qui parle de la dictée écrit **exactement** `<strong><span style="white-space:nowrap;">Windows + H</span></strong>` - jamais abrégé, jamais en graisse normale, jamais coupé en fin de ligne. À vérifier sur tout nouveau module / écran / correction, au même titre que les accents (§0bis) et le tiret court. Détail : `docs/TACHES_VALIDEES.md`, section « Autres tâches en attente ».
- **Jamais garder un mécanisme (bouton, badge, champ d'état) par habitude ou parce qu'il est déjà codé.** Rencontré le 2026-08-25 (module Repères) : "prêt à en parler" (état privé/partagé) et "Discuté" existaient depuis longtemps, mais Denis a demandé de justifier concrètement leur utilité avant de les garder dans la nouvelle architecture - vérification dans le code (grep) : ces champs n'étaient lus NULLE PART ailleurs que par leur propre badge/bouton/filtre, conçus à l'origine pour un partage bénéficiaire → CIP jamais devenu possible techniquement. Aucun argument solide trouvé, retirés entièrement (champs, badges, boutons, filtre). **Règle** : pour tout mécanisme dont on doute de l'utilité, chercher dans le code un usage concret AILLEURS que son propre affichage - s'il n'y en a pas, ce n'est pas neutre à garder. Pour un public en fragilité numérique, un contrôle sans effet visible ailleurs coûte de la confusion pour rien, ce n'est jamais un simple "au cas où".
- **Toute fenêtre ou panneau doit toujours offrir un moyen visible de la fermer/quitter**, jamais seulement un second clic sur l'icône qui l'a ouverte (geste peu évident une fois le regard porté sur le panneau lui-même, pas sur l'icône d'origine). Rencontré 2 fois séparément (Carnet, puis Repères/Journal de parcours le 2026-08-25) : Denis a signalé l'absence de croix de fermeture comme une sensation d'être "prisonnier" du panneau. Toute nouvelle fenêtre/panneau doit recevoir sa croix dès sa conception, même mécanisme que `.carnet-panneau-fermer`/`.reperes-journal-fermer` - jamais après coup, sur signalement.

- **Jamais un bloc de texte qui tombe d'un coup sur un écran de rapport/résultat.** Toujours découper en chapitres/sous-chapitres repliés par défaut (accordéons), avec une courte description visible et le détail complet seulement au clic. La personne doit pouvoir choisir la quantité d'information qu'elle veut voir, et dans l'ordre qu'elle préfère (certains veulent commencer par les points forts, d'autres par les points faibles) - jamais un ordre de lecture imposé. Ce principe existe déjà en partie dans le rapport du Bilan (accordéons par axe). S'applique à tout écran de rapport/résultat, pas seulement au Bilan. Ne concerne que l'AFFICHAGE d'un diagnostic déjà produit - une étape de correction/validation séquentielle (un pas après l'autre) reste un cas différent, avec sa propre justification, pas concernée par cette règle.

### 1sexies. Animations et pulses : jamais de risque photosensible, intensité et distance IDENTIQUES partout

**Signalé plusieurs fois par Denis, formalisé le 2026-08-28 ("j'ai l'impression que je vais faire une crise d'épilepsie").** C'est un vrai sujet de sécurité (photosensibilité), pas une question de goût.

**Règles :**
1. **Jamais rien qui clignote vite ou fort.** Pas de cycle sous ~1,5 s pour une animation qui tourne en continu, jamais de flash de contraste brutal, jamais de changement de taille marqué (`transform: scale`) sur une animation infinie.
2. **Intensité, distance ET couleur uniformes sur TOUTE l'application.** Standard : tout pulse est un anneau `box-shadow` qui part de `color-mix(in srgb, var(--accent) 40%, transparent)` et s'étend à `8px`, sans grossissement. **Décision Denis 2026-08-31 : une SEULE couleur de pulse = l'accent du thème (`var(--accent)`, bleu par défaut, suit la couleur d'accent et le mode daltonien).** Les anciennes couleurs porteuses de sens (jaune = perdu, gris = sauvegarde, vert = non sauvegardé) sont abandonnées : sur fond blanc à côté d'une icône bleue elles juraient, et une couleur unique se repère plus facilement et reste cohérente avec la charte. Keyframe unique `pulseAccentPersistant` (`css/style.css`). **Toute nouvelle animation de pulse reprend ce standard tel quel.** Une intensité/distance/couleur différente n'est admise que si Denis l'a explicitement demandée pour ce cas précis.
3. **Aucun pulse infini.** Standard en place (2026-08-28) : cadence `1.8s`, borné à `6` répétitions (≈ 10 s), puis l'animation s'arrête d'elle-même. Un pulse tourne aussi jusqu'à la première interaction (survol/clic) si le JS le retire à ce moment-là. Les quelques pulses bornés plus courts ou plus longs (5 s, 15 s) ont été réglés explicitement avec Denis pour leur contexte précis - ne pas les uniformiser sans lui demander. Jamais `infinite` sur un pulse (le seul `infinite` légitime restant est le spinner de chargement `demo-video-tourner`).
4. **Respecter `prefers-reduced-motion`.** Une règle globale existe en fin de `css/style.css` (ajoutée le 2026-08-28) - ne jamais la contourner avec un `!important` sur une animation.
5. Avant d'ajouter une animation quelconque : `grep "@keyframes"` dans `css/style.css` et les CSS de modules pour voir le standard réel et s'y conformer, jamais réinventer une courbe/intensité.
6. **Un seul élément pulse à la fois sur l'écran, jamais deux, jamais cinquante.** Plusieurs pulses simultanés = perturbant et illisible (on ne sait plus où regarder). Dès qu'un système peut faire pulser plus d'un élément, il faut un **ordre de priorité explicite** : le pulse le plus prioritaire s'affiche, les autres se suspendent tant qu'il est actif. **Fait pour l'accueil le 2026-09-01** (`js/app.js`, commit `722b972`) : coordinateur `_pulsePersistantDemander(btnId, classe, dureeMs, priorite)` / `_pulsePersistantLiberer(btnId)` / `_pulsePersistantViderTout()`. Priorité des 3 boutons du haut : **disquette (2) > aide/ampoule (1) > préférences/œil (0)**. L'infobulle « i » d'un panneau de carte ouvert passe devant tout (`brancherInfoCarteAccueil` appelle `_pulsePersistantViderTout()`). **Tout nouveau pulse persistant DOIT passer par ce coordinateur**, jamais un `classList.add('aide-pulse-…')` + `setTimeout` isolé. Pour les pulses ponctuels d'un autre contexte : toujours se demander « qu'est-ce qui pulse déjà ailleurs à ce moment-là ? ».

## 1bis. Un prompt par module, jamais un prompt fourre-tout

**Ne jamais fusionner les consignes de plusieurs modules dans un seul prompt IA, même si ça semble économiser un aller-retour.** Un prompt trop long/trop chargé fait que l'IA laisse tomber une partie des consignes, surtout celles situées vers la fin - pas une théorie, un fait déjà vérifié deux fois :
- Le prompt V3 (fusion diagnostic+extraction du Bilan) a été testé, déployé, puis retiré le jour même : en usage réel, l'IA ne produisait pas toujours le bloc extraction malgré la consigne explicite.
- Décision prise le 2026-08-25 pour le chantier Cohérence transversale : plutôt que d'ajouter toute l'analyse croisée CV/lettre/entretien dans `prompts/bilan-v1.md` (déjà dense, 9 axes + un schéma JSON strict), un prompt entièrement séparé a été créé pour ce nouveau module.

**Règle pour tout futur module qui a besoin d'une analyse IA** : lui donner son propre prompt dédié, même si une partie du raisonnement ressemble à un prompt déjà existant. On peut s'inspirer d'un prompt existant (structure, ton, contraintes de style comme "jamais de tiret long"), mais jamais le réutiliser tel quel en y ajoutant des sections supplémentaires. Un prompt focalisé sur une seule mission reste fiable ; un prompt qui essaie de tout faire à la fois perd en fiabilité, même si chaque instruction individuelle est correcte.

## 1ter. Deux types de messages, jamais confondus

Un message destiné à **Denis** (dans le chat) et un message destiné à **une autre IA** (un brief à relayer) ne sont pas le même exercice :

- **Pour Denis** : court, clair, sans mot technique non expliqué. Denis n'est pas développeur/ingénieur/codeur - il porte ce projet par passion, avec une vision produit large mais pas un métier technique. S'il veut plus de détail, il le demande lui-même.
- **Pour une autre IA** (un brief que Denis va copier-coller ailleurs) : peut être long, précis, technique - Denis ne le lit pas en profondeur, il le relaie tel quel.

**Règle** : avant d'écrire une réponse pendant la conception d'un module, se demander à qui elle s'adresse. Ne jamais mélanger les deux dans un seul message.

**Confirmation explicite, jamais silencieuse** : quand Denis donne une consigne (y compris une consigne générale, pas seulement une tâche de code), la confirmer explicitement une fois appliquée - jamais juste l'appliquer en silence et enchaîner sur autre chose. Sans ça, Denis ne sait pas si la consigne a été lue, comprise, déjà faite, ou ignorée - il redemande alors inutilement, ce qui interrompt le travail en cours pour rien.

### 1quater. Ajouter une route vers un module autonome casse les tests Node si le stub DOM n'est pas mis à jour

Rencontré le 2026-08-25, chantier Cohérence transversale : `js/app.js` référence directement `pageXxx` (une fonction vivant dans le fichier `<script>` du nouveau module, jamais dans `app.js` lui-même) dans l'objet littéral `routes`. Sous Node, `require()` ne fait jamais fuiter les fonctions d'un module vers le scope global (contrairement à un `<script>` navigateur) - `tests/_domStub.js` stub donc explicitement `pageReperes`/`pageCarnet`/`pageLexique` en fonctions vides pour permettre aux tests qui font `require('../js/app.js')` de fonctionner.

**Règle** : chaque fois qu'une nouvelle entrée `'nom-route': pageXxx` est ajoutée à `routes` (`js/app.js`) pour un module dont la fonction de page vit dans un autre fichier, ajouter aussi `pageXxx` à la liste stubée dans `tests/_domStub.js` - sinon tous les tests qui chargent `js/app.js` sous Node échouent d'un coup (`ReferenceError: pageXxx is not defined`), sans rapport apparent avec le code réellement testé.

## 1quinquies. Un style repris d'un brouillon précédent sans y repenser n'est pas un choix, c'est un oubli qui coûte cher à retrouver

Rencontré le 2026-08-27, maquette "Porte d'entrée" : les boutons "Confidentialité de vos données" et "Retour sur votre expérience" avaient un style gris discret (`.bouton-pied`), alors que les 5 icônes persistantes juste au-dessus avaient été rendues bleues et cohérentes le même jour. Aucune des deux couleurs n'était un vrai choix pensé pour CETTE version - le gris venait d'un style "bouton discret" créé dans une maquette antérieure de la même session (`Boussole`), recopié par habitude sans se demander s'il convenait encore une fois le reste de la page passé au bleu cohérent. Denis a posé une question toute simple ("est-ce un choix délibéré, et si oui pourquoi ?") qui a suffi à révéler qu'il n'y avait pas de vraie justification - seulement une inertie.

**Règle** : chaque fois qu'un style est copié depuis un écran ou une maquette précédente (même dans la même session), se demander explicitement s'il reste justifié dans le nouveau contexte, plutôt que de le recopier par réflexe parce que "ça a déjà cette forme ailleurs". Un style non réévalué n'est pas un choix de conception, même s'il finit par ressembler à un choix a posteriori - dès qu'on ne peut pas expliquer POURQUOI un élément est différent des autres, c'est probablement un oubli, pas une décision, et il faut le traiter comme tel : le corriger, pas le justifier après coup.

## 2. Navigation

- **Le bouton "Retour" doit toujours ramener à l'écran précédent, jamais à l'accueil.** Point de vigilance identifié comme non résolu de façon générale : `barreNavigation()` (`js/app.js`) utilise aujourd'hui une destination codée en dur par écran plutôt qu'un vrai historique, alors qu'un historique réel existe déjà techniquement (`history.pushState`/`popstate`, câblé seulement à la flèche du navigateur). Un correctif local existe dans le Bilan, la portée globale reste à traiter (voir `docs/ETAT_DES_CHANTIERS_2026-08-24.md`, section 3, "RC-03"). **Pour tout nouvel écran créé : vérifier explicitement que son bouton Retour ramène bien à l'écran d'où l'on vient, pas à un écran fixe par défaut.**
  - **Rencontré à nouveau le 2026-08-25** : tous les écrans du module Cohérence transversale (1er ET 2e prompt) appellent `barreNavigation('cv', ...)` telle quelle, donc "Retour" ramène systématiquement à l'accueil (page CV), jamais à l'écran précédent du parcours - repéré par Denis sur l'écran "Choisissez votre assistant" de l'entretien avancé, alors qu'un bouton dédié juste à côté ("Retour au rapport") faisait déjà correctement la bonne action. `options.onclickPrecedent` (déjà prévu dans `barreNavigation()`, déjà utilisé par `pageResultats()`) permet de remplacer la destination par défaut - à utiliser systématiquement dans un module à plusieurs écrans internes, jamais laisser la valeur par défaut `'cv'` sans y réfléchir explicitement pour chaque écran.
  - **Variante « boucle infinie », rencontrée sur « Co-construire ma lettre » (corrigée 2026-09-07) PUIS sur « Regard recruteur » (corrigée 2026-09-08, même patron).** Dans un module famille 2, le bouton « Retour » de la barre du bas et le bouton « Revoir la présentation » ne doivent PAS partager la même fonction. « Revoir la présentation » ouvre la page d'intro **en mode détour** (dont le propre « Retour » / « Revenir au module » renvoie *dans* le module) : si « Retour » appelle aussi cette fonction, les deux boutons se pointent l'un l'autre et on ne peut plus reculer jusqu'à l'accueil. **Règle** : un seul `xxxRetour()` / `xxxAllerVersPrecedent()` partagé par la barre du bas ET (s'il existe) le bouton contextuel, qui recule **d'un cran à la fois** ; depuis le tout premier écran de travail, il ouvre la présentation **en mode NORMAL** (pas détour), pour que le « Retour » de la présentation continue ensuite vers l'accueil de la carte. `xxxRetourVersPresentation()` (détour) reste réservé au SEUL bouton « Revoir la présentation ». Patron correct de référence : `_comprendreLesChiffresAllerVersPrecedent()`, `_coLettreRetourIntro()`, `regardRecruteurRetour()`.
    - **Balayage complet le 2026-09-09** (demande de Denis, « regarder partout »). La MÊME boucle existait encore, non corrigée, dans **9 modules** : la famille 1 (`Lexique`, `Carnet`, `Repères` - la barre du bas de l'unique écran de travail appelait `xxxRevoirPresentation()` / `_reperesForcerAccueil = true`, détour), la famille 2 (`Analyser ma candidature`, `Cohérence de mon dossier`, `Comparer mes pistes`, `Découvrir mes compétences`) ET les deux modules de « Se tenir informé » (`Comprendre le cadre`, `Comprendre les chiffres` - depuis l'accueil du module, `_xxxAllerVersPrecedent()` appelait `_xxxRevoirPresentation()`, détour). Toutes corrigées le même jour, même patron : nouvelle fonction `xxxRetour()` sur la barre du bas → présentation en mode **normal**. Cas particuliers : `Repères` et `Cohérence` réutilisaient un seul drapeau pour deux intentions (détour de consultation VS vrai recul) → il a fallu **ajouter un second drapeau** (`_reperesRetourAccueil`, `_ctRetourAccueil`), consommé une seule fois par le dispatcher, pour que la présentation s'affiche en mode normal sans toucher au flag du détour. `Bilan` : `_etatBilan.voirIntro` est passé de booléen à `'detour'` | `'normal'`. Pour `Comprendre le cadre` / `Comprendre les chiffres`, un seul drapeau (`_comprendreLeCadreDetourPresentation` / `_comprendreLesChiffresDetourPresentation`) suffisait : `xxxRetour()` le met à `false` avant de naviguer vers la présentation, `_xxxRevoirPresentation()` le met à `true`. **Modules déjà corrects avant ce balayage** : Co-construire ma lettre, Préparer un entretien, Regard recruteur, ATS. **La portée globale de cette variante est donc traitée** - mais rester vigilant sur tout nouveau module à page d'introduction.

## 3. Aide contextuelle et bouton guide

- Tout nouvel écran/fenêtre doit recevoir une entrée dans `AIDE_PAGES`/`AIDE_FENETRES` (`js/app.js`), avec le même ton simple et rassurant que les entrées déjà écrites - ce n'est pas automatique, il faut y penser explicitement à chaque nouvel écran, ce n'est pas toujours fait.
- Le bouton d'aide fixe/flottant doit rester actif et pertinent sur tout nouvel écran, pas seulement sur les écrans déjà couverts par le chantier "aide contextuelle toutes fenêtres" (2026-08-03).

## 4. Suivi d'usage (Umami)

- Toute nouvelle action importante (ouverture d'un écran, validation d'une étape, acceptation/rejet d'une proposition IA...) doit recevoir un événement Umami, sur le même modèle que les événements déjà en place. Facile à oublier en codant une fonctionnalité, à vérifier systématiquement avant de considérer un module terminé.

### 4bis. Un champ créé mais jamais réellement branché jusqu'au bout

Rencontré le 2026-08-25, pendant le chantier Cohérence transversale : un nouveau champ (`siteEntreprise`) a été exposé côté lecture de données, mais la zone de saisie qui devait l'alimenter n'était reliée nulle part - la donnée existait, mais n'arrivait jamais réellement jusqu'au prompt envoyé à l'IA.

**Règle** : après avoir créé ou exposé un nouveau champ de saisie, une nouvelle donnée lue, ou une nouvelle zone de texte, **vérifier explicitement toute la chaîne jusqu'au bout** - pas seulement que le champ existe et se lit correctement, mais qu'il est bien utilisé par le consommateur final (le prompt envoyé à l'IA, ou l'écran qui l'affiche). Un champ exposé mais jamais consommé plus loin est une fausse impression de fonctionnalité.

## 5. Zéro régression, en particulier aux points de connexion

- Le risque le plus concret n'est pas dans un module isolé, mais **au moment où on le branche à l'existant**. Exemple réel déjà rencontré : la collision entre le Bilan et l'ancien module IA de la page Action, qui effaçait silencieusement des corrections déjà faites (corrigé, commit `603f002`). **Chaque fois qu'un nouveau module lit ou écrit une donnée déjà utilisée ailleurs dans l'app, vérifier explicitement qui d'autre lit/écrit cette même donnée, pas seulement tester le nouveau module isolément.**
- Toujours tester dans un vrai navigateur avant/après, jamais se contenter d'une relecture de code (règle déjà ancienne, toujours valable).

## 6. Écriture

- Toujours en français correct, avec tous les accents, jamais d'anglicisme ni de mot compliqué - le public cible a une compréhension parfois fragile, la simplicité n'est pas optionnelle.
- **Jamais de tiret long/cadratin (—) ni de double-tiret (--)** dans un texte visible, ni dans le code/les commentaires. Toujours le tiret court (-). Règle déjà appliquée sur tout le dépôt (sweep terminé 2026-08-04), mais à respecter systématiquement dans tout nouveau texte écrit.
- **Toujours le nom complet "lettre de motivation" et "préparation d'entretien d'embauche" dans les textes visibles par la personne** (règle posée le 2026-08-25, chantier Cohérence transversale) - jamais raccourci en "lettre" ou "entretien" seuls. Raison donnée par Denis : ces raccourcis sont un vocabulaire de conseiller ("pour aller plus vite"), pas celui d'un bénéficiaire qui découvre l'outil - la précision aide à comprendre de quoi on parle réellement. Exception : "CV" reste "CV" (déjà un raccourci compris de tous, contrairement aux deux autres). Vérifier ce point à chaque nouveau texte, pas seulement au moment de l'écrire une première fois - facile à oublier en cours de route.
- **Mettre en gras les mots qui désignent une fonctionnalité concrète qui aide la personne** (règle posée le 2026-08-25, chantier Cohérence transversale, à partir de "dictée vocale"/"Windows + H") - dès qu'un texte mentionne un moyen concret d'agir plus facilement (dicter au lieu de taper, répondre par la voix, une combinaison de touches précise...), mettre ce passage en gras pour qu'il ressorte visuellement dans la phrase, jamais noyé dans un paragraphe explicatif. S'applique à chaque nouvelle apparition de ce type de mention, pas seulement à l'endroit où la règle a été demandée la première fois.
- **Éviter le mot "IA" de façon explicite dans les textes visibles par la personne** (règle posée le 2026-08-25, chantier Cohérence transversale) - préférer "assistant" seul, ou une formulation neutre. Raison donnée par Denis : une partie réelle des bénéficiaires ET des CIP en insertion professionnelle est sceptique voire mal à l'aise face à l'IA, souvent perçue comme une menace pour l'emploi - l'app ne doit pas accentuer ce sentiment par un vocabulaire trop explicitement technologique. Même logique pour les icônes : éviter la tête de robot, préférer un symbole plus neutre/humain (accompagnement). **Portée pas encore tranchée à l'échelle de toute l'app** (beaucoup d'écrans existants disent déjà "assistant IA") - vérifier avec Denis avant d'étendre ce sweep au-delà du module en cours de modification.

## 7. Accessibilité, à garder à l'esprit dès maintenant

Le chantier formel d'accessibilité viendra plus tard (voir [[project_sequencement_modules_accessibilite_decoupage]]), mais chaque nouvel écran construit d'ici là devrait déjà, sans effort supplémentaire notable : avoir un contraste de couleur correct, être utilisable au clavier (on peut en sortir, le focus est visible), et donner un texte compréhensible par un lecteur d'écran aux boutons/icônes (pas juste une icône seule sans description).

### 7bis. Un module "récent"/"tardif" dans la séquence n'est jamais moins prioritaire côté explication

Rencontré le 2026-08-25, chantier Cohérence transversale : l'écran "Choisissez votre assistant" construit pour ce module manquait le bloc "Ce qui va se passer" (4 étapes numérotées + déclencheur de vidéo de démonstration) déjà présent sur l'écran équivalent du Bilan (`htmlBilanEtapeChoixIA()`, `js/app.js`) - repris à la légère en pensant qu'un module plus tard dans la séquence pouvait s'appuyer sur une version simplifiée.

**Règle** : une personne qui utilise Cohérence transversale (ou tout autre module construit tard dans la feuille de route) peut très bien être une toute première visite sur l'application - la position d'un module dans l'ordre de construction ne dit rien sur l'expérience réelle de la personne qui l'utilise. Ne jamais réduire le niveau d'explication/d'accompagnement d'un écran sous prétexte qu'il arrive "plus tard" dans le projet. Toujours comparer un nouvel écran à l'écran équivalent déjà existant le plus complet (pas le plus simple) avant de le considérer terminé.

**Rencontré à nouveau le 2026-08-25, quelques heures plus tard, DANS LE MÊME CHANTIER** : l'écran "Choisissez votre assistant" de l'entretien avancé (2e prompt du même module) a été construit sans le bloc "Ce qui va se passer" ni le déclencheur de vidéo, exactement la même simplification déjà identifiée et corrigée ci-dessus le même jour, sur l'écran équivalent du 1er prompt. Preuve concrète que "je viens de corriger ça" ne suffit pas à empêcher la récidive sur un écran voisin construit juste après, dans le même module, par la même personne (l'assistant qui code) - la vigilance doit être réappliquée à CHAQUE écran individuellement, jamais supposée acquise pour le reste du chantier en cours.

**Rencontré ENCORE le 2026-08-28 (Carte 3 du Bilan)** : la fenêtre `bilanOuvrirChoixAssistantLot()` (choix de l'assistant pour générer les formulations en lot, Carte 2 + Carte 3) n'affichait que les pastilles d'assistants, sans le bloc "Ce qui va se passer" ni la vidéo. Corrigé le jour même. **Règle renforcée, DEMANDE EXPLICITE DE DENIS (2026-08-28) : "toute fenêtre/écran qui renvoie la personne vers une plateforme IA doit être la version COMPLÈTE - jamais un raccourci."** Cela veut dire systématiquement : (a) les 4 étapes numérotées "Ce qui va se passer" (constante `ETAPES_DETAIL_CHOIX_IA` ou une variante au contenu adapté, ex. `ETAPES_DETAIL_CHOIX_IA_LOT` pour la génération de formulations), détail affiché au clic ; (b) le déclencheur de vidéo de démonstration (`htmlDeclencheurDemoVideo('export-ia-texte')`) ; (c) le rappel de confidentialité. La version "simple/allégée" de ces fenêtres ne sera proposée QUE dans le futur module Accessibilité, via une bascule globale (voir [[project_sequencement_modules_accessibilite_decoupage]]) - jamais codée en dur ailleurs.

**Détail de mise en page à ne pas rater** : les 4 pastilles d'étapes doivent tenir sur UNE SEULE LIGNE. Sur un écran pleine largeur, le libellé "Ce qui va se passer" peut rester en colonne de 130px à gauche. Dans une **fenêtre modale** (plus étroite), la 4e pastille passe à la ligne - il faut alors mettre "Ce qui va se passer" sur sa propre ligne au-dessus, et la rangée de pastilles en `flex-wrap:nowrap` (avec `overflow-x:auto` de sécurité). Vu et corrigé sur `bilanOuvrirChoixAssistantLot()` le 2026-08-28.

### 7ter. Un module qui garde son état hors de `dossier` est invisible à la disquette ET à "Réinitialiser"

Rencontré le 2026-08-25 : `sauvegarderSession()`/`restaurerSession()` (`js/app.js`, "la disquette") ne capturent que l'objet `dossier` - tout module qui garde ses propres données ailleurs (objectif de portabilité, ex. `modules/coherence-transversale/core/diagnosticStore.js`, `modules/bilan-candidature/core/diagnosticStore.js`) est silencieusement perdu à la fermeture du navigateur ou à la restauration d'un fichier de session. Même famille de bug pour `recommencer()` ("Réinitialiser la session") : `bilanStoreReinitialiser()` y était déjà appelé (bug EX-17, corrigé une 1ère fois), mais `ctStoreReinitialiser()` avait été oublié pour Cohérence transversale, module plus récent - un diagnostic périmé pouvait survivre à un "nouveau départ".

**Règle** : tout module qui garde son état hors de `dossier` doit exposer 2 fonctions au nom standard - `xxxExporterEtatPourSauvegarde()` (retourne `null` si rien d'actif) et `xxxRestaurerEtatDepuisSauvegarde(etat)`. `sauvegarderSession()`/`restaurerSession()`/`importerSessionFichierSelectionne()` (`js/app.js`) les appellent via `collecterEtatsModulesPourSauvegarde()`/`restaurerEtatsModules()`, sans jamais connaître le détail interne de ces modules. **À chaque nouveau module de ce type : (1) lui ajouter ces 2 fonctions, (2) les enregistrer dans `collecterEtatsModulesPourSauvegarde()`/`restaurerEtatsModules()`, (3) vérifier que son store a aussi une fonction "reinitialiser" appelée depuis `recommencer()`.**

## 7quater. Une idée qui ne trouve pas sa place dans le module en cours n'est jamais abandonnée silencieusement

Décidé le 2026-08-27, pendant la conception de la barre de recherche élargie. Denis propose parfois une idée qui, après réflexion commune, ne convient pas au module en cours de discussion - pas parce qu'elle est mauvaise, mais parce que ce module n'a pas la fonction/l'architecture pour l'accueillir. **Règle** : cette idée doit être notée dans `docs/IDEES_A_RECLASSER.md` (fichier commun à toute IA du dépôt, créé ce jour-là), avec le contexte d'origine et une recommandation de module plus adapté - ou "sans module identifié" si aucun ne convient encore. Avant de concevoir un nouveau module, vérifier si des idées accumulées dans ce fichier y trouvent enfin leur place ; plusieurs idées "sans module" partageant un thème commun peuvent annoncer un module qui n'existe pas encore.

## 8. Modularité et portabilité

- Un nouveau module doit rester le plus autonome et indépendant possible - objectif explicite de Denis : pouvoir un jour récupérer un module et l'intégrer tel quel dans un autre site/projet.
- Éviter d'alourdir encore `js/app.js` (déjà ~29 000 lignes) quand une fonctionnalité peut raisonnablement vivre dans son propre fichier/dossier, sur le modèle déjà appliqué à `modules/bilan-candidature/`, `modules/reperes/`, etc.

## 9. Motifs de bugs réellement rencontrés plusieurs fois (relevé git, 2026-08-06 -> 2026-08-24)

Analyse de tous les commits de correction sur cette période (24 commits repérés). Certains motifs reviennent plusieurs fois, sous des habillages différents - ce sont ceux-là qu'il faut vraiment retenir.

### 9.1 Mode sombre : couleurs fixes en hexadécimal sans couleur de texte explicite

Rencontré **3 fois** (Carnet, astuce Découverte + bannière transition IA, et le même motif signalé comme probablement présent ailleurs sans être encore corrigé). Cause à chaque fois identique : un encart utilise un fond/une bordure en couleur fixe (ex. `#EFF6FF`/`#BFDBFE`) sans fixer explicitement la couleur du texte - le texte hérite alors de `--text-strong`, qui devient clair en mode sombre, sur un fond resté clair : texte quasi invisible.

**Règle** : ne jamais coder une couleur de fond/bordure en hexadécimal fixe pour un nouvel encart. Toujours utiliser les variables CSS déjà prévues pour ça (`--accent-bg-subtle`, `--accent`, `--text-strong`...), qui ont déjà leurs versions claires ET sombres. **Tester systématiquement tout nouvel encart coloré en mode clair ET en mode sombre avant de le considérer terminé.**

### 9.2 Neutraliser un style de bouton en n'écrasant qu'une partie de la propriété

`.btn-famille-explorer` ne fixait que `border-color`, jamais `border`/`background` en entier - une bordure fixée par le style de base (Bootstrap) restait donc visible au survol malgré la couleur "transparente" demandée.

**Règle** : quand on neutralise visuellement un bouton/lien pour qu'il n'ait aucune boîte visible, fixer explicitement `border` et `background` en entier (pas seulement leur couleur), pour être sûr qu'aucun état (survol, focus, visité) ne fasse réapparaître une bordure par défaut.

### 9.3 Un élément d'interface disparaît silencieusement sur un chemin non testé

Rencontré **2 fois**, deux causes différentes mais la même famille de bug :
- Le bouton Importer de Découverte disparaissait parce qu'un composant partagé (`activerCollageInstantane`) exigeait des identifiants qu'un des deux parcours qui l'utilisent (Découverte) ne fournissait pas.
- Le panneau Personnaliser de l'Atelier CV disparaissait parce que, sur les 2 boutons qui mènent au même grand aperçu, un seul des deux synchronisait correctement l'état du panneau - l'autre l'oubliait.

**Règle** : quand une fonctionnalité est accessible par **plusieurs chemins/boutons différents**, ou quand on branche un **nouveau parcours sur un composant déjà partagé par un autre**, vérifier explicitement que chaque chemin déclenche bien la même synchronisation d'état - ne jamais valider seulement le chemin "principal" testé en premier.

### 9.4 Un texte/message devient contradictoire avec le comportement réel après un changement ailleurs

Rencontré **3 fois** : un écran promettait moins que ce qu'il faisait réellement ("ne peut pas être automatisé" alors qu'une génération assistée existait juste en dessous), un message de réassurance évoquait justement l'idée qu'on voulait éviter d'installer dans la tête de la personne, et - le cas le plus sérieux - **le prompt envoyé à l'IA du Bilan se contredisait lui-même** : il demandait d'anonymiser le CV avant analyse, mais le moteur signalait ensuite l'absence de coordonnées comme une anomalie, parce qu'un détecteur lisait une donnée interne (`dossier.identite`) au lieu du texte réellement envoyé à l'IA (anonymisé par conception).

**Règle** : après avoir modifié un comportement ou une consigne, chercher activement tous les textes qui en parlent - **dans l'app ET dans les prompts IA** - et vérifier qu'ils restent cohérents. Un détecteur/test automatique doit toujours être vérifié sur la même donnée que celle réellement utilisée dans le flux, jamais une donnée "proche" mais différente.

### 9.5 Une fenêtre rejoue son animation d'ouverture à chaque petit rafraîchissement

`ouvrirFenetreERIP()` recréait toute la boîte (animation, défilement remis à zéro, focus volé) à chaque rafraîchissement de contenu, même quand ce n'était pas un vrai changement d'écran - d'où un effet de "tremblement" au moindre clic.

**Règle** : pour un écran à contenu dynamique qui se met à jour souvent, distinguer explicitement un simple rafraîchissement (même titre déjà affiché) d'un vrai changement de fenêtre - ne rejouer l'animation d'entrée/le focus initial que pour ce dernier.

### 9.7 Un contrôle interactif laissé HORS du conteneur qu'on rafraîchit accumule ses écouteurs jusqu'au gel du navigateur

Rencontré le 2026-08-25, module Repères, signalé par Denis (page qui se fige complètement après 3-4 clics sur le filtre "Tous mes Repères"/"Prêts à en parler", au point qu'un rafraîchissement de la page elle-même ne répondait plus). Cause : les 2 boutons de filtre étaient rendus une seule fois, EN DEHORS du conteneur régénéré à chaque clic (`#reperesListeConteneur`, remplacé via `innerHTML =` par la fonction de rafraîchissement) - mais la fonction qui rebranche les écouteurs de clic était, elle, rappelée à CHAQUE rafraîchissement, et reposait un nouvel écouteur sur ces 2 boutons sans jamais retirer les précédents (`querySelectorAll` non scopé au conteneur, boutons jamais détruits donc jamais "nettoyés" par `innerHTML =`). Accumulation exponentielle : 2 écouteurs après le 1er clic, 4 après le 2e, 8 après le 3e, 16 après le 4e - chaque écouteur déjà posé se redéclenchant et en reposant un nouveau à chaque clic suivant. Même cause a produit un 2e symptôme signalé séparément par Denis : les boutons ne changeaient jamais visuellement d'état actif après le premier clic (rendus une seule fois, jamais recréés avec la bonne classe `is-active`).

**Règle** : tout élément interactif (bouton, filtre, onglet...) dont l'état visuel ou le comportement doit refléter les changements d'un conteneur rafraîchi régulièrement doit vivre **À L'INTÉRIEUR** de ce conteneur - jamais à côté, même si ça semble plus économique de ne pas le "regénérer inutilement". Une fonction qui rebranche des écouteurs à chaque rafraîchissement doit toujours être appariée à un `innerHTML =` qui détruit réellement les anciens nœuds concernés juste avant - sinon chaque rebranchement s'additionne au lieu de remplacer. Symptôme à reconnaître : un gel du navigateur qui apparaît seulement après plusieurs clics répétés au même endroit (jamais au 1er clic) est une signature quasi certaine d'accumulation d'écouteurs, pas un simple ralentissement.

### 9.8 Une icône positionnée dynamiquement par rapport à une autre peut lire un rectangle encore faux (invisible, ou pas encore repositionné)

Rencontré le 2026-08-25, module Repères/Carnet, signalé par Denis (l'icône Carnet superposée au panneau/à l'icône Journal de parcours - "je vois que j'ai un carnet et des notes une sur l'autre"). Deux icônes persistantes (`#btnCarnet`, `#btnJournalParcours`) se positionnent en JS via `positionnerIconePersistante(idBouton, idBoutonReference)` (`js/app.js`), chacune calée sous le bas de sa "référence" - un mécanisme délibérément choisi pour éviter une valeur fixe en pixels qui recasse au premier changement de hauteur de page. Le piège : `#btnJournalParcours` démarre `hidden` par défaut dans `index.html` (masqué tant qu'aucun Repère n'existe) - un élément caché a un rectangle à zéro (`getBoundingClientRect()`), donc toute icône qui le prend pour référence AVANT qu'il soit révélé se positionne au mauvais endroit, et ne se corrige jamais toute seule ensuite (le calcul ne se relance qu'à la prochaine navigation réelle, pas quand l'icône de référence change juste de visibilité en cours de session).

**Règle** : dans une chaîne d'icônes positionnées les unes par rapport aux autres, toujours faire pointer chaque icône vers une référence qui est fiable en permanence (jamais masquée conditionnellement) plutôt que vers une référence qui peut apparaître/disparaître selon les données de la personne - sinon l'ordre d'initialisation devient fragile et les symptômes (superposition) n'apparaissent que dans certains scénarios (première visite sans données, session restaurée...), pas systématiquement, ce qui les rend difficiles à repérer en test rapide. Si une icône conditionnelle doit exister dans la chaîne, la placer en DERNIER (jamais comme référence d'une autre), et repositionner tout ce qui en dépend au moment précis où sa visibilité change, pas seulement à la prochaine navigation.

**RÉCIDIVE le même jour (2026-08-25, signalée à nouveau par Denis, 5e/6e fois selon lui)** : le réordonnancement ci-dessus (Carnet référence fiable, Journal placé en dernier) a bien réglé le cas du tout premier chargement, mais PAS le cas où le premier Repère est créé **en cours de session, sans navigation entre-temps** (ex. directement depuis la page "Mes Repères", en cliquant "+ Garder une réflexion"). Cause précise : `_reperesMettreAJourJournal()` (la fonction qui bascule `bouton.hidden` de vrai à faux dès qu'un Repère existe) ne repositionnait jamais le bouton lui-même à cet instant précis - elle se contentait de le révéler, en s'appuyant sur la valeur CSS statique de repli (152px). Cette valeur suppose que `#btnCarnet` est à sa position par défaut (90px) - fausse dès que `#btnCarnet` a été repositionné plus bas par JS sur la page courante (titre sur 2 lignes, barre de progression plus haute...). Exactement le 2e conseil du paragraphe précédent, qui n'avait pas été appliqué à cette icône-là : **une icône conditionnelle doit se repositionner elle-même (pas seulement ce qui dépend d'elle) au moment exact où SA PROPRE visibilité change**, pas seulement à la prochaine navigation. Corrigé en appelant `_reperesPositionnerBoutonJournal()` explicitement dans `_reperesMettreAJourJournal()`, juste après avoir révélé le bouton.

**Point de méthode retenu de cette récidive** : Denis a signalé que le bug "disparaissait" après un F5 - piège de diagnostic, pas une preuve de correction. Un F5 recharge aussi `dossier` à vide (rien n'est auto-restauré sans clic explicite sur "Restaurer"), donc le Repère qui causait le bug disparaît EN MÊME TEMPS que le bug lui-même. Ne jamais conclure qu'un F5 qui fait disparaître un symptôme confirme une correction : il faut recréer les conditions exactes (ici : créer le tout premier Repère alors qu'on est DÉJÀ sur une page, sans navigation) pour vérifier réellement.

### 9.9 L'icône phare d'un module doit rester identique partout où elle apparaît

Rencontré le 2026-08-26, module Repères, signalé par Denis (capture d'écran) : au moment de choisir ⚓ comme icône d'identité du module (écran d'accueil, bouton "Revoir l'explication"), le `<h1>` de l'écran principal ("Mes Repères") gardait encore l'ancienne icône 📌 juste à côté - deux icônes différentes pour désigner la même chose, sur la même ligne. En creusant plus loin : le bouton d'ancrage réel `_reperesRenduBoutonAncre()` (« Garder comme Repère », inséré dans d'autres modules comme Cohérence transversale ou Bilan) utilisait 📋, la tuile de la Boîte à outils utilisait `bi-bookmark` (Bootstrap Icons), et deux textes d'aide dupliqués (`js/app.js`, `modules/coherence-transversale/ui.js`) affichaient encore une 3e icône (📌) dans leur propre titre - jusqu'à 4 icônes différentes pour désigner le même concept selon l'endroit.

**Règle** : dès qu'un module a une icône d'identité choisie (pas une icône de sous-catégorie interne, comme les 4 types de Repère qui gardent chacun la leur), cette icône doit être la SEULE utilisée partout où ce module/concept est représenté - écran principal, boutons d'ancrage insérés dans d'autres modules, tuile de la Boîte à outils, textes d'aide qui le décrivent. Un changement d'icône décidé à un endroit doit systématiquement déclencher une recherche (`grep`) de toutes les autres occurrences du même concept avant d'être considéré terminé, jamais seulement corrigé à l'endroit où le besoin a été remarqué.

**Renforcement, demande explicite de Denis, 2026-08-30** (maquette « Analyser ma candidature » : la page d'introduction parlait de « Mes Repères » **sans** l'icône ⚓). Élargissement : **dès qu'un texte, un bouton, une carte ou une phrase fait référence par son nom à un module / une fonction / un bouton qui a déjà sa propre icône identifiée, cette icône DOIT être posée à côté du nom.** Nommer « Mes Repères », « Mon Carnet », « Lexique », « Cohérence de mon dossier »… sans son icône est une erreur, pas un détail. Vaut aussi pour les maquettes. Corollaire : quand une référence à un autre module mérite d'être mise en avant (pas une simple mention en passant), elle va **dans son propre encart / rectangle**, avec l'icône en tête - jamais noyée dans une puce au milieu d'une liste.

### 9.10 Une classe utilitaire Bootstrap (`.text-muted`...) n'est jamais adaptée au mode sombre, et gagne même contre une règle plus spécifique si on oublie `!important`

Rencontré le 2026-08-26, module Repères, signalé par Denis (captures d'écran : texte disparaissant complètement en mode sombre - "mots-clés à chercher", l'avertissement sur les liens, le texte "Par Repère"). Cause : `.text-muted` (utilisée dans des dizaines d'écrans de toute l'app, pas seulement Repères) vient de Bootstrap, jamais réécrite pour `[data-theme="sombre"]` nulle part dans `css/style.css` - son gris quasi noir (`rgba(33,37,41,.75)`) devient quasi invisible sur n'importe quel fond sombre. Piège supplémentaire découvert en corrigeant : Bootstrap 5.3 déclare cette règle en **`!important`** (`color: var(--bs-secondary-color) !important`, vérifié dans `bootstrap.min.css`) - un premier correctif écrit sans `!important` avait une spécificité CSS plus forte (`[data-theme="sombre"] .text-muted`) mais perdait quand même contre Bootstrap, silencieusement, sans erreur ni avertissement visible. Le bug est resté invisible à une simple relecture de code : il fallait vraiment charger la page en mode sombre et regarder.

**Règle** : (1) toute classe utilitaire Bootstrap de couleur de texte (`.text-muted`, `.text-danger`, `.text-primary`...) utilisée dans l'app doit avoir sa propre règle `[data-theme="sombre"] .text-xxx { color: ... !important; }` dans `css/style.css` - vérifier explicitement laquelle Bootstrap utilise-t-il (`!important` ou non, `grep` dans le fichier Bootstrap servi) avant d'écrire le correctif, jamais supposer qu'une spécificité plus forte suffit. (2) Corriger une seule fois, à la source (`css/style.css`), jamais écran par écran - une classe Bootstrap utilitaire est par nature partagée par toute l'app. (3) **Chaque fois qu'on écrit ou modifie un texte/écran, vérifier son rendu réel en mode sombre avant de le considérer terminé** (basculer `data-theme="sombre"` et regarder, pas seulement grep le CSS) - un texte invisible ne casse rien techniquement (pas d'erreur console, pas de test qui échoue), il ne se voit qu'à l'œil.

### 9.11 Recentrer/élargir un panneau qui vivait dans un coin peut le faire recouvrir une vraie fenêtre d'action - une nouvelle fenêtre doit TOUJOURS passer devant celle déjà ouverte

Rencontré le 2026-08-26, module Repères, signalé par Denis (2 captures d'écran) : le panneau "Journal de parcours" (`z-index:2700`, même palier que les icônes utilitaires persistantes comme `#btnAide`, volontairement toujours cliquables) a été recentré et élargi sur demande de Denis (voir plus haut). Une fois centré, il s'est mis à recouvrir toute vraie fenêtre d'action ouverte DEPUIS lui (choisir un type de Repère, modifier un Repère existant) - ces fenêtres passent par `ouvrirFenetreERIP()`, dont l'overlay est à `z-index:2000`, plus bas. Tant que le panneau restait dans son coin d'origine, ce conflit n'existait pas : il ne recouvrait jamais une fenêtre elle-même centrée. Symptôme trompeur pour Denis : il pensait manquer un bouton "Annuler" alors qu'il existait déjà (la croix de fermeture) - simplement invisible, cachée derrière le panneau.

**Règle** : une fenêtre/panneau qui déclenche l'ouverture d'une AUTRE fenêtre par-dessus lui ne doit jamais la recouvrir - la nouvelle fenêtre est toujours prioritaire visuellement, quel que soit le point de départ. Distinguer clairement, pour tout panneau à icône persistante (Carnet, Journal...) : l'ICÔNE elle-même peut légitimement rester dans le palier "toujours cliquable" (2700, au-dessus de `ouvrirFenetreERIP()`), mais son CONTENU (le panneau qui s'ouvre) n'a pas besoin de ce même niveau - il doit rester SOUS `.fenetre-erip-overlay` (2000, `css/style.css`) pour ne jamais bloquer une vraie fenêtre d'action déclenchée depuis lui. Ne jamais résoudre ce genre de conflit en fermant automatiquement le premier panneau (mauvaise expérience si la personne veut y revenir) - toujours corriger l'empilement (z-index) à la place. **Dès qu'un panneau existant change de taille/position (recentré, élargi...), vérifier explicitement s'il peut désormais en recouvrir une autre - pas seulement si son propre contenu reste lisible.**

### 9.12 Certains émojis contiennent eux-mêmes du texte anglais dessiné dans leur glyphe - jamais les utiliser dans une app en français

Rencontré le 2026-08-26, maquette "Lecture des Rapports" (module Repères), signalé par Denis via une capture d'écran. En cas de doute, préférer un émoji purement graphique (symbole, forme, objet - ex: 🔔 ✏️ ✨ ⚓) plutôt qu'un émoji "signalétique" de ce type. Ce n'est pas visible en lisant le nom de l'émoji dans le code - seul un rendu visuel réel (capture d'écran, ou question directe à la personne) le révèle.

### 9.15 Deux boutons voisins avec des intentions qui se ressemblent, mais des mécanismes différents, créent une vraie confusion - jamais supposer que la personne devine laquelle choisir

Rencontré le 2026-08-26, module Repères/Regard extérieur. "Aller plus loin" (pose des questions ciblées avant un 2e passage IA) et "Demander un Deuxième Regard" (renvoie les mêmes Repères sans aucune question) ont été construits l'un après l'autre, tous deux décrits à Denis comme "un passage plus approfondi chez l'assistant" - assez proche pour qu'il utilise le second en s'attendant au comportement du premier, et soit déçu par un résultat pauvre (aucune question, peu de matière nouvelle) sans comprendre pourquoi. Pire : l'assistant (ce compte) a d'abord mal diagnostiqué la plainte de Denis, affirmant à tort un "bug de nom de champ JSON" dans le mauvais prompt, sans avoir vérifié à quel fichier le JSON collé correspondait réellement (comparaison champ par champ faite seulement après coup, sur demande explicite de Denis).

**Règle** : (1) quand deux fonctionnalités voisines ont des noms/descriptions qui se ressemblent mais un comportement réellement différent (ex. "avec questions" vs "sans questions"), le distinguer EXPLICITEMENT dans le texte visible à l'endroit du choix, jamais seulement dans un commentaire de code - la personne choisit sur ce qu'elle lit à l'écran, pas sur l'intention du développeur. (2) Avant d'affirmer la cause d'un problème signalé (surtout un "bug technique"), vérifier concrètement les données réelles en cause (ex. comparer un JSON collé, champ par champ, aux schémas des DEUX prompts possibles) plutôt que de supposer laquelle des deux fonctionnalités proches a été utilisée - une explication plausible mais non vérifiée peut être fausse et il faut le dire clairement dès qu'on s'en rend compte, sans minimiser l'erreur.

### 9.16 Vérifier une URL avant de l'ajouter à une liste blanche, même quand elle "semble" correcte - et accepter de dire "pas de source fiable" plutôt que d'en inventer une

Rencontré le 2026-08-26, prompts Regard extérieur, en ajoutant de nouvelles ressources demandées par Denis (aide alimentaire, mobilité solidaire, PLIE). Deux URLs "raisonnables" devinées de mémoire (`www.union-plie.org`, `www.alliance-villes-emploi.fr`) se sont révélées inexistantes (échec DNS) une fois vérifiées via WebFetch - alors que 4 autres URLs, vérifiées de la même façon avant d'être ajoutées (Croix-Rouge, Solidarauto, Banques Alimentaires, Secours Populaire, Restos du Cœur), étaient toutes exactes. **Règle** : pour toute app qui interdit explicitement les URLs devinées (voir la liste fermée de Regard extérieur), vérifier RÉELLEMENT chaque nouvelle URL avant de l'écrire dans un prompt ou dans le code (WebFetch ou équivalent) - "ça semble être la bonne adresse" n'est jamais suffisant, deux échecs sur six tentatives dans cette même session le confirment. Quand aucune source nationale fiable n'existe pour un dispositif pourtant réel, le dire honnêtement et proposer une orientation générique (interlocuteur, pas de lien) plutôt que de risquer un lien mort pour un public qui a déjà peu de marge d'erreur.

### 9.17 Une croix de fermeture peut être invisible-cliquable : hauteur de fenêtre non bornée + ordre d'empilement, deux pièges différents avec le même symptôme

Rencontré le 2026-08-27, maquette "Porte d'entrée" (réorganisation de la Boîte à outils). Denis a signalé que la croix de fermeture d'une fenêtre "ne fonctionnait que sur un petit endroit". Deux causes distinctes trouvées en testant réellement les coordonnées de clic (`elementFromPoint`), jamais visibles à la simple relecture du CSS : (1) la fenêtre n'avait pas de `max-height`/`overflow-y` - sur un écran pas assez haut, le centrage vertical (`align-items:center`) pousse le haut du contenu (dont la croix) hors du viewport, rendant une partie de la croix littéralement hors champ. (2) Un bloc de titre positionné (`position:relative`), placé APRÈS la croix dans le HTML, passait au-dessus d'elle dans l'ordre d'empilement (aucun z-index explicite nulle part) - la croix recevait alors les clics d'un autre élément invisible par-dessus elle, sans aucun signe visuel du problème.

**Règle** : toute fenêtre modale doit avoir une hauteur maximale avec défilement interne (jamais laisser son contenu pousser hors de l'écran). Tout bouton de fermeture doit recevoir un `z-index` explicite et supérieur au reste du contenu de la fenêtre - ne jamais compter sur le seul ordre du HTML pour garantir qu'il reste cliquable, surtout dès qu'un autre élément positionné (`position:relative`/`absolute`) est ajouté plus tard dans la même fenêtre. Un clic "qui ne marche que par endroits" est une signature quasi certaine d'un élément invisible superposé, pas d'un problème de taille de zone cliquable - vérifier avec les coordonnées réelles (`elementFromPoint` ou équivalent) plutôt que de deviner à l'œil.

### 9.19 Récupérer un tracé SVG via un outil qui résume (WebFetch) peut le corrompre silencieusement

Rencontré le 2026-08-27, icône "ampoule" (aide) de la maquette "Porte d'entrée". Le tracé récupéré une première fois via WebFetch avait été coupé en 2 `<path>` séparés à un endroit où le vrai fichier n'en contient qu'UN SEUL avec un "moveto" au milieu (`...A5.98 5.98 0 0 1 2 6` puis `m6-5a5 5 0 0 0...` dans la MÊME chaîne `d=`) - un outil qui résume via un petit modèle peut mal réinterpréter une longue chaîne de chiffres compacts (arcs SVG). Résultat visuel : une forme cassée que Denis a décrite comme "une tête", pas une ampoule claire. Corrigé en redemandant explicitement le contenu brut caractère par caractère, dans un bloc de code, sans résumé.

**Règle** : pour un tracé SVG dense (beaucoup de chiffres collés, arcs, `m`/`a` en minuscule), toujours redemander explicitement le contenu BRUT et complet ("character by character, no summarization"), jamais se contenter d'un premier résumé - surtout si le rendu final semble visuellement étrange. Une forme qui "ressemble à autre chose que prévu" est un signe fort de tracé corrompu à la source, pas seulement un mauvais choix d'icône.

### 9.20 Dupliquer la position d'un panneau à la main, séparément de son bouton, recrée le même bug à chaque déplacement

Rencontré 2 fois de suite le 2026-08-27, maquette "Porte d'entrée". Première fois : en déplaçant 3 boutons (rotation réglages/aide/disquette demandée par Denis), leurs panneaux respectifs sont restés à l'ancienne position - personne ne les avait déplacés avec les boutons, corrigé à la main. Deuxième fois, quelques échanges plus tard : 2 nouveaux boutons (Confidentialité, Retour sur expérience) avaient eux aussi une position de panneau écrite en dur, sans lien réel avec la position du bouton - le panneau s'ouvrait n'importe où par rapport à lui.

**Règle** : ne jamais écrire la position d'un panneau séparément de celle de son bouton déclencheur, même "juste pour cette fois" - calculer TOUJOURS la position du panneau à partir de la position réelle du bouton au moment de l'ouverture (`getBoundingClientRect()`), jamais deux valeurs dupliquées à la main à deux endroits différents du code. Ce n'est pas qu'une question de propreté : c'est le seul moyen de rendre ce bug précis impossible à reproduire, plutôt que de compter sur le fait de s'en souvenir à chaque futur déplacement de bouton.

**Complément trouvé le même jour, un peu plus tard** : calculer la position seulement à L'OUVERTURE ne suffit pas si le bouton déclencheur n'est pas lui-même `position:fixed` - un bouton dans le flux normal de la page (ex. un bouton de pied de page) défile AVEC la page au scroll, mais un panneau `position:fixed` reste, lui, figé à l'écran : les deux se désynchronisent dès qu'on fait défiler après ouverture, même si la position de départ était juste. **Règle complémentaire** : recalculer la position du panneau ouvert à CHAQUE défilement (`window.addEventListener('scroll', ...)`), pas seulement au clic d'ouverture - sinon le bug ne se voit qu'en scrollant après avoir ouvert le panneau, un test qui clique puis relit la position immédiatement ne le détecte jamais.

### 9.21 Une fonction "fermer" qui vide aussi le champ ne doit jamais être appelée pendant la frappe elle-même

Rencontré le 2026-08-27, maquette "Porte d'entrée", barre de recherche. Denis avait demandé un comportement réel : en fermant le tiroir de résultats (croix, clic ailleurs, Échap), le champ de recherche doit se vider - pas de texte fantôme au retour. Implémenté comme une seule fonction `masquerResultat()` qui fait les deux choses (cacher le tiroir + vider `champRecherche.value`). Problème : cette même fonction était aussi appelée depuis `chercher()` chaque fois que le texte tapé faisait moins de 2 caractères, pour cacher le tiroir tant qu'il n'y a rien à afficher. Résultat : à CHAQUE frappe (le premier caractère fait toujours moins de 2), le champ était aussitôt vidé - la personne tapait, rien ne s'affichait jamais, la barre semblait totalement figée/cassée. Denis a d'abord suspecté un problème de navigateur/clavier/extension (testé en navigation privée, rien à voir), avant de pointer lui-même la vraie cause : "ça a cassé pile au moment où j'ai demandé le comportement du clic-dehors-efface".

**Règle** : dès qu'une fonction "fermer/annuler" fait plus d'une chose (cacher + vider + réinitialiser...), ne jamais la réutiliser telle quelle pour un cas qui ne veut qu'UNE SEULE de ces choses. Séparer en deux fonctions distinctes (ex. `masquerDropdown()` qui cache seulement, `masquerResultat()` qui cache ET vide) plutôt que d'appeler la version "complète" par réflexe parce qu'elle existe déjà. Un bug qui empêche totalement de taper dans un champ, alors que le clavier fonctionne partout ailleurs (testé par la personne dans d'autres fenêtres, d'autres apps), pointe presque toujours vers du code qui touche `.value` à chaque frappe - jamais vers l'environnement.

### 9.18 Une infobulle en `position:absolute` a l'intérieur d'une fenêtre qui défile (`overflow-y:auto`) grandit la zone de défilement elle-même

Rencontré le 2026-08-27, maquette "Porte d'entrée", infobulle sur "Mes documents". Denis a signalé qu'au survol, une barre de défilement apparaissait sur la fenêtre et que le message semblait "faire partie" de la fenêtre plutôt que flotter par-dessus. Cause : la bulle était en `position:absolute`, positionnée par rapport à un ancêtre à l'intérieur de la fenêtre modale (qui a `overflow-y:auto`) - un élément absolument positionné reste compté dans le `scrollHeight` de son ancêtre défilant le plus proche, même s'il est "sorti du flux" pour la mise en page de ses voisins. Corrigé en passant la bulle en `position:fixed` (échappe entièrement au calcul de défilement de tout ancêtre, sauf si un ancêtre a un `transform`/`filter`/`will-change` qui recrée un contexte de positionnement - vérifié qu'aucun n'en a ici), avec sa position calculée en JS (`getBoundingClientRect()` du déclencheur) plutôt qu'en CSS pur.

**Règle** : toute bulle/popover destinée à flotter par-dessus une fenêtre qui peut défiler doit être en `position:fixed` (jamais `absolute`) si elle vit dans le même arbre DOM que la zone qui défile - sinon elle agrandit silencieusement la zone de défilement, même si visuellement elle a l'air de "juste flotter". Vérifiable en comparant le `scrollHeight` du conteneur bulle ouverte vs fermée : s'il change, la bulle n'est pas correctement sortie du flux de défilement.

### 9.22 Le contour de focus par défaut du navigateur peut prendre une couleur inattendue (orange) selon les réglages du système - à fixer explicitement partout où on force `.focus()` en JS

Rencontré le 2026-08-27, maquette "Porte d'entrée", croix de fermeture de "Mes documents". `ouvrirFenetreERIP()`-like code appelle `panneauFermer.focus()` a l'ouverture (accessibilite clavier). Sans règle CSS dédiée, le navigateur affiche son propre contour de focus par défaut, dont la couleur dépend du système/des réglages d'accent Windows du visiteur - Denis l'a vu orange, une couleur qui donne involontairement envie de cliquer dessus, l'inverse de l'effet voulu pour une croix de fermeture neutre.

**Règle** : tout élément sur lequel le code appelle `.focus()` par programmation doit avoir sa propre règle `:focus-visible` explicite (couleur neutre choisie par l'app, ex. `var(--text-muted)`), jamais laisser le navigateur choisir. Point additionnel découvert au passage, pas encore corrigé : la touche Tab depuis cette croix sort de la fenêtre modale vers des boutons en arrière-plan (pas de piège de focus) - à traiter dans un futur chantier accessibilité.

### 9.13 Une "copie figée" prise trop tôt fige aussi les défauts qu'un traitement ultérieur devait corriger

Rencontré le 2026-08-26, module Regard extérieur, chantier nettoyage automatique par IA des Repères. `_regardExterieurCreerRapport()` construit `reperesConcernes` comme une copie figée (`titre`/`texte`) du Repère au moment de l'appel - principe voulu et documenté ("jamais un lien vers eux"). Le nouveau code de nettoyage automatique (`reperesAppliquerNettoyageIA()`, qui remplace le titre/texte du Repère par la version proposée par l'IA) avait été placé APRÈS l'appel à `_regardExterieurCreerRapport()` - le rapport se retrouvait donc figé pour toujours avec l'ANCIEN texte brut (dictée non nettoyée) dans `reperesConcernes`, alors même que le Repère lui-même, consulté séparément dans "Mes Repères", affichait déjà la version propre. Trouvé uniquement en testant un vrai import de bout en bout dans le navigateur (données fabriquées mais flux réel) et en lisant le contenu affiché, jamais en relisant le code seul.

**Règle** : avant de figer une copie de données (snapshot, `Object.assign({}, x)`, tableau construit une fois pour toutes...), vérifier qu'AUCUN traitement censé modifier ces données n'a lieu APRÈS ce point - sinon la copie fige la version d'AVANT ce traitement, silencieusement, sans erreur. Réordonner pour que toute transformation (nettoyage, normalisation, enrichissement) ait lieu avant la construction de toute copie qui doit refléter le résultat final. Vérifier aussi les valeurs déjà extraites plus tôt dans le même flux (ex. un champ résolu au parsing) qui pourraient devoir être réassignées après coup, pas seulement le point de copie principal.

### 9.14 `--success`/`--success-strong` : même piège que `.text-muted` (9.10), trouvé une deuxième fois dans le VRAI `css/style.css`

1. **Avant d'agir sur toute note de session antérieure** (dans `TACHES_VALIDEES.md`, une mémoire d'assistant, un commentaire de code, un `docs/*`, y compris un plan « verrouillé » présenté comme « vérifié »), la re-vérifier dans le vrai code courant - dans les deux sens : "marqué à faire mais peut-être déjà fait" ET "marqué fait/mort mais peut-être encore vivant". Une note reflète l'état du dépôt au jour où elle a été écrite, pas forcément aujourd'hui - et un plan peut citer un point de branchement qu'un autre chantier a déplacé depuis. `git log`/`grep` sur les identifiants concernés, tracer le chemin d'appel depuis son point d'entrée réel, jamais la seule lecture de la note.
2. **Pour prouver qu'une branche de code est morte** : partir de la variable d'état qui sélectionne cette branche (ici `_etatCorrectionBilan.mode`), lister TOUTES ses écritures (`grep` exhaustif), puis pour chacune remonter à la fonction qui écrit et lister TOUS ses appelants. Vérifier en plus : aucun `onclick=`/`data-*` dans le HTML qui passe la valeur, aucune restauration de session qui réinjecte l'état (`sauvegarderSession()` ne sérialise que `dossier`/`historique`/`page`/`modulesEtat`), aucun test qui force la valeur. Tant que ces trois vérifications ne sont pas faites, "c'est probablement mort" n'autorise pas la suppression.
3. **`js/app.js` et les `modules/*/ui.js` ne sont JAMAIS chargés par les tests Node** (`node --test "tests/*.test.js"`, 63 fichiers) - ils testent la logique pure des modules, jamais le DOM ni `app.js`. Donc pour toute suppression/modification dans `app.js`, le SEUL filet de sécurité est un passage navigateur réel de chaque chemin voisin qui partage du code avec ce qui est touché (ici : les modes `libre`, `copier`, l'écran de clôture, et l'Assistance à la finalisation, qui partagent `bilanDeclencherActionCorrection`/`_bilanStatutsCorrection`/`bilanBoutonQuitterCorrection`). Ne jamais conclure "tests verts donc pas de régression" pour un changement `app.js`.

### 9.24 Un `sed`/`perl` de masse pour remplacer du texte dans le code : 3 pièges qui cassent des fichiers

**Rencontré le 2026-08-28, chantier « vocabulaire IA neutre » (remplacer « IA » par « assistant » dans ~30 fichiers).**

1. **Une apostrophe droite `'` dans le remplacement, injectée dans une chaîne JS `'...'`, ferme la chaîne et casse le fichier.** `s/réponse IA/réponse de l'assistant/` appliqué à `'... la réponse IA ...'` produit `'... la réponse de l'assistant ...'` -> `SyntaxError`. **Toujours utiliser l'apostrophe COURBE `’`** dans les remplacements (elle ne délimite jamais une chaîne JS), jamais l'apostrophe droite. Le dépôt mélange déjà les deux dans les textes utilisateur, donc `’assistant` est cohérent.
2. **`perl -i -pe "s/.../’/g"` SANS `binmode` ré-encode les caractères accentués de chaque ligne touchée en mojibake** (`é` -> `Ã©`). L'avertissement « Wide character in print » est le signe. **Ne jamais utiliser perl pour ça** - `sed` gère l'UTF-8 correctement.
3. **`sed -i` réécrit TOUT fichier qu'on lui passe, même sans substitution** - un glob trop large (`modules/**/*.js`) marque des dizaines de fichiers comme modifiés (fin de ligne / newline finale normalisées), noyant le vrai diff. **Cibler les fichiers un par un**, ou vérifier `git diff` fichier par fichier avant de committer.

**Méthode sûre** : pour un remplacement de texte dans le code, préférer des `sed` ciblés sur une liste explicite de fichiers, apostrophe courbe uniquement, `node -c` sur chaque fichier touché + `git diff` relu, jamais un glob récursif ni perl.

4. **Ajout 2026-08-29 — un script Python de remplacement en masse ancré sur un motif qui n'est PAS unique détruit du contenu silencieusement.** Un patch qui remplaçait le bloc `relations:` de 11 fiches Lexique cherchait, à partir de `id: 'X',`, le prochain `\n    ]`. Pour `discrimination-embauche` dont `relations: []` est en une seule ligne (pas de `\n    ]`), la recherche a continué et avalé **3 fiches entières** jusqu'au `\n    ]` suivant. Détecté par `node scripts/checkLexique.js` (« référence une fiche inconnue »), restauré via `git checkout`. **Règle** : un remplacement scripté doit matcher une chaîne exacte connue (pas « jusqu'au prochain motif »), gérer les formes courtes (`[]` vs `[\n…\n]`), passer par un `assert count == 1` sur chaque ancre, et être suivi de `node -c` + du validateur du domaine (`checkLexique`) AVANT tout commit. Toujours pouvoir `git checkout` (ne rien committer tant que la vérification n'est pas verte).

### 9.25 Générer des `id` qui rejoignent une collection écrite à la main : le garde-fou d'idempotence masque une vraie collision au lieu de la signaler

Rencontré le 2026-08-28, étape 8 du chantier freins : les 17 fiches « frein » sont générées depuis `data/freins.js` et poussées dans `LEXIQUE_FICHES` (corpus rédigé à la main dans `data/lexique.js`). L'id généré `'frein-' + code` valait `'frein-emploi'` pour le code `emploi` — or `frein-emploi` existe déjà comme fiche rédigée à la main (la notion générale « Frein à l'emploi »). Le garde d'idempotence `LEXIQUE_FICHES.some(x => x.id === id)` (prévu pour ne pas ré-injecter au rechargement) a **silencieusement avalé la collision** : 16 fiches créées au lieu de 17, aucune erreur. Trouvé uniquement en comptant dans le navigateur (`LEXIQUE_FICHES.filter(f => f.univers === 'freins-parcours').length` = 16). Corrigé en préfixant `'freins-' + code` (pluriel) — aucun id `frein-*` existant ne peut alors coïncider.

**Règle** : quand on génère des id destinés à être fusionnés dans une collection contenant déjà des entrées écrites à la main, choisir un préfixe/namespace qui ne peut PAS coïncider avec un id existant (vérifier la vraie liste des id). Ne jamais compter sur un garde d'idempotence pour révéler une collision : il est fait pour l'inverse (éviter un doublon de soi-même) et masque le problème. Vérifier explicitement le compte final (`N générés == N attendus`), en test ou en navigateur.

### 9.31 `git mv` puis éditer le fichier : le renommage est indexé, PAS les modifications de contenu qui suivent

**Trouvé le 2026-09-05, migration du contenu de « Comprendre le cadre » (`docs/CONTENU_COMPRENDRE_LE_CADRE/` vers `modules/comprendre-le-cadre/contenu/`).**

Pour 5 fichiers (rayons handicap, jeunes, juridique), le `git mv` avait bien indexé le renommage, mais les **éditions de contenu faites juste après sont restées non indexées** - `git commit` (sans `-a`, sans `git add`) a donc committé les fichiers **au nouvel emplacement mais avec l'ancien contenu**. Les corrections étaient perdues du commit, présentes seulement dans le working tree. Rattrapé par un commit dédié `641e5ef` (`git add` explicite des 5 fichiers, message qui explique le rattrapage).

Autre piège de la même migration : `git rm` **refuse** un fichier qui a des modifications locales (« file has local modifications ») - il faut `git rm -f`, après avoir vérifié qu'on veut bien jeter ces modifications.

**Règle** : après un `git mv` suivi d'éditions du fichier déplacé, **toujours `git add` explicitement le fichier** avant de committer (ou `git add -A` après un `git status` relu ligne à ligne). Ne jamais faire confiance à `git commit` seul pour ramasser des éditions post-`mv`. Vérifier `git show --stat HEAD` juste après le commit : le nombre de lignes changées doit correspondre aux corrections réellement faites, pas seulement au renommage (`R100`).

Prolonge 9.9 (icône phare identique partout) appliqué aux **libellés**.

### 9.34 Un parseur « tolérant » de contenu à main levée : construire d'abord le fichier au format que le parseur attend, jamais l'inverse

**Chantier « Comprendre les chiffres », blocs 3-4 (2026-09-06).** Le module lit des fichiers `contenu/<mois>.md` produits par l'outil de veille. En codant le parseur en premier puis en écrivant le contenu « à peu près », plusieurs bugs sont apparus au navigateur : une parenthèse `(dont 19 % depuis deux ans)` prise pour une date ; un `**gras**` coupé en deux `<p>` parce que le paragraphe d'intro était écrit sur deux lignes ; « environ 51 000 offres diffusées » + un gabarit de phrase « ont été diffusées » = redondance ; des comparaisons entre `17 500 personnes` et `+1,7 %` mises côte à côte parce que le parseur ne distinguait pas la nature.

**Règle** : (1) le format du fichier de contenu et le parseur se décident ENSEMBLE - écrire un exemple de fichier complet, le passer dans le parseur, corriger les deux jusqu'à ce que le rendu soit juste, AVANT de généraliser. (2) Une regex de date ne matche que ce qui ressemble à une date (année, « trimestre », « provisoire »), jamais « la première parenthèse ». (3) Un gabarit de phrase ne doit jamais répéter un mot déjà dans la valeur : soit la valeur porte l'unité (« 51 000 offres »), soit la phrase, jamais les deux. (4) Ne jamais afficher côte à côte deux nombres de nature différente (un compte et un pourcentage) : un helper `mêmeNature(a, b)` garde-fou.

### 9.35 Les fichiers de contenu d'un module s'écrivent en français impeccable comme le reste - le front-matter aussi dès qu'une valeur est affichée

**Même chantier.** Les trois `contenu/*.md` ont d'abord été écrits sans accents (`avril a juin`, `chomage localise`, `offres diffusees`), par réflexe « c'est de la donnée, pas du texte d'interface ». **Règle** : un fichier de contenu lu par l'application est du texte d'interface. Accents partout, y compris dans les valeurs de front-matter qui s'affichent (`periode`, `prochaine_maj`...). Seules les **clés** de front-matter et les identifiants techniques restent en ASCII.

### 9.36 Un graphe en barres d'une valeur qui bouge peu : choisir une base qui ne transforme pas 0,2 point d'écart en barre 5 fois plus courte

**Même chantier.** Le premier graphe SVG de la couche 1 partait d'une base `min - (max - min) * 0.25`. Pour une série 7,6 / 7,6 / 7,6 / 7,8, ça donnait des barres dans un rapport de 1 à 5 : visuellement, le taux avait « explosé ». C'est un mensonge par l'échelle.

**Règle** : pour un indicateur qui varie de quelques dixièmes, la base du graphe doit rester assez basse (`min - max((max-min) * 1.5, |min| * 0.1, 0.5)`) pour que la plus petite barre garde une hauteur crédible. La maquette d'origine le faisait déjà (rapport ~1,25 pour un écart de 0,5 point) : la reprendre, pas réinventer une échelle plus « lisible ».

### 9.37 Avant d'écrire une fiche « Comprendre le cadre », grep le corpus de fiches, pas seulement le registre de liens

**Le 2026-09-08.** Une fiche `emploi-clause-sociale-insertion` a été écrite, testée, committée (`d418529`), puis découverte en doublon de `accompagnement-clause-sociale-plie` déjà en ligne (même sujet, même source `economie-clauses-sociales`, même intention). **Règle** : avant de créer une fiche, `grep -rli "<mots-clés du sujet>" modules/comprendre-le-cadre/contenu/` en excluant les `.collecte.md`. Le sujet peut déjà vivre dans un **autre rayon** que celui auquel on pense (ici : la clause sociale est un sujet « accompagnement / structures de l'insertion », pas « contrats de travail »). C'est l'application directe du non-négociable « une seule source de vérité, jamais de duplication » : il vaut pour le contenu autant que pour le code.

### 9.38 Élargir une condition de rendu sans élargir la garde de câblage EXACTEMENT pareil : une page entière devient inerte

**Le 2026-09-16, page "Votre objectif"**, signalé par Denis avec une frustration pleinement justifiée ("je ne peux rien choisir sur cette page", "toute la page objectif que je ne peux pas cliquer") après une série d'allers-retours déjà éprouvante ce jour-là. En élargissant le bloc entreprise/destinataire de "Votre objectif" à candidature spontanée/reconversion (commit `e16c646`), le RENDU (`contenuModeRecherche()`) a bien été élargi correctement, imbriqué dans `if (mode === 'metier') {...} else if (mode === 'domaine') {...}` - ce bloc n'existe donc dans le DOM QUE si un mode a déjà été choisi. Mais la garde de CÂBLAGE (`wireModeRecherche()`, plus bas dans le même fichier) a été élargie séparément, en revérifiant seulement `dossier.objectif`/`dossier.typeRecherche` - jamais `dossier.modeRecherche`, la vraie condition qui décide si le bloc existe réellement dans le DOM à cet instant. Résultat : dès l'arrivée normale sur "Votre objectif" (aucun mode encore choisi - l'état de TOUTE personne au premier chargement, pas un cas limite), `bilanCablerCiblageOffre()` cherchait un champ absent du DOM, un `addEventListener` sur `null` levait une exception qui arrêtait net le reste de `wireModeRecherche()` - y compris le câblage des boutons "métier précis"/"domaine" plus bas dans cette même fonction. Plus rien de cliquable sur toute la page : un bug bien plus grave que celui qu'on cherchait à corriger, et provoqué par le correctif lui-même. Rattrapé le jour même en urgence (`2ded754`).

**Règle** : quand une condition de rendu conditionnel (`if (x) { html += ... }`) est élargie, la garde de câblage qui lui correspond doit être élargie EXACTEMENT PAREIL - jamais en redécrivant la même condition métier "de mémoire" un peu plus loin dans le fichier (risque réel de diverger, même sans le vouloir). Le plus sûr : faire vérifier au câblage la **présence réelle de l'élément dans le DOM** (`zone.querySelector('#monChamp')`) plutôt que de deviner si le rendu a dû avoir lieu - une seule source de vérité, jamais deux conditions à maintenir en synchronisation à deux endroits différents. Symptôme à reconnaître : une exception JS non interceptée au milieu d'une fonction de câblage arrête tout ce qui vient APRÈS elle dans cette même fonction, sans erreur visible ailleurs qu'en console - un écran qui devient "tout entier inerte" après une modification ciblée en est la signature quasi certaine, jamais un simple ralentissement à traiter au fil de l'eau.

**Règle complémentaire, sur comment ça a échappé à la vérification avant de committer** : le test au navigateur fait juste avant ce commit portait sur l'état "mode déjà choisi" (celui qu'on venait de construire/vérifier), jamais sur l'état RÉEL de première arrivée sur l'écran (mode pas encore choisi) - exactement l'inverse d'un vrai premier passage. Après toute modification d'un écran à choix progressifs (jetons, étapes, accordéons), tester systématiquement l'état "rien n'est encore choisi" en plus de l'état qu'on vient de construire - c'est souvent l'état le plus fréquent en usage réel (toute nouvelle personne qui arrive), et le plus vite oublié en test parce qu'on reste concentré sur le cas qu'on vient de coder.

## 10. Méthode de travail : maquette/questions AVANT code dès qu'il y a un doute, corrections regroupées par bloc

> **Voir aussi `docs/TRAVAILLER_AVEC_DENIS.md`** (créé le 2026-08-28) : longueur des réponses attendue (court et direct par défaut, code `[détaillé]` / `[relais IA]`) et gestion des jours de fatigue de Denis (une seule reco, Claude tranche les évidences, toujours signaler une décision douteuse avec la meilleure option en premier). Fichier commun à tous les comptes / toutes les IA, à charger à chaque nouvelle tâche.

Rencontré le 2026-08-26, module Repères, chantier du petit bouton "i" informatif du Journal de parcours - signalé explicitement par Denis comme un problème de méthode, pas seulement un bug technique. Denis a demandé un bouton "i" à un endroit qu'il avait clairement en tête, avec un comportement précis. L'assistant a codé sa PROPRE interprétation à chaque étape sans jamais vérifier cette interprétation avant d'écrire du code, ce qui a produit une succession de corrections, chacune révélant un nouveau malentendu :
1. Icône flottante séparée dans la colonne Carnet/Journal (Denis voulait "à l'intérieur" du panneau).
2. Fenêtre modale (`ouvrirFenetreERIP`) au clic (Denis voulait une bulle au survol, "on a déjà fait ce fonctionnement quelque part").
3. Bulle positionnée AU-DESSUS du bouton, invisible car coupée par le débordement du panneau (`overflow-y:auto`) - jamais testée par une vraie capture d'écran avant de la donner comme terminée.
4. Bulle qui restait bloquée affichée après un clic (`:focus` au lieu de `:focus-visible`).

Denis estime que cette succession d'allers-retours lui a coûté l'équivalent de 20% du temps d'usage d'une session entière - un coût réel, pas juste une gêne.

### Règle 1 : dès qu'il y a le moindre doute sur un placement, un comportement ou une fonction d'un élément d'interface, poser des questions concrètes AVANT de coder

Questions à se poser explicitement, et à poser à Denis si la réponse n'est pas déjà claire : où exactement doit se trouver l'élément ? Quel geste (clic, survol, les deux ?) déclenche quoi ? Que se passe-t-il ensuite, et quand est-ce que ça s'arrête/se ferme ? Quels cas limites (mobile, clavier, contenu qui déborde) ?

**Exceptions, où on peut coder directement sans reposer la question** :
- la consigne est déjà sans ambiguïté réelle ;
- un bug est déjà identifié avec certitude, et la correction ne risque pas de le reproduire ;
- la compréhension de ce que veut Denis sur CE point précis a déjà été validée plus tôt dans le même échange.

### Règle 2 : dès qu'il y a un doute, privilégier une MAQUETTE interactive (Artifact) avant le vrai code

Une maquette se retravaille sans toucher au code réel - moins chère et plus rapide à corriger qu'un aller-retour code → capture d'écran → nouvelle explication du dysfonctionnement → nouveau code. Denis veut voir concrètement les boutons, les placements, les fonctions dans la maquette, itérer dessus autant que nécessaire, puis valider explicitement ("tout est cohérent, plus rien à changer") avant que le codage commence. Ne pas coder en parallèle "au cas où" pendant que la maquette est encore en discussion.

**Précision demandée par Denis le 2026-08-28** : quand une maquette enchaîne PLUSIEURS écrans et que tous ne sont pas nouveaux (certains existent déjà dans l'application, montrés seulement pour la continuité du parcours), le dire clairement écran par écran - un bandeau en haut de chaque écran ("Nouvel écran, à concevoir" vs "Écran déjà dans l'application"), et un mot sur les transitions coupées (ex. sur l'écran de génération : "en vrai, ici, vous copiez un texte, vous le collez dans une IA, vous récupérez la réponse ; ici c'est simulé"). Sans ça, Denis peut croire que TOUTE la maquette est du nouveau à valider, et se perdre entre ce qui est déjà acté et ce qui reste à décider. Vu sur la maquette Carte 3 (`docs/MAQUETTE_CARTE3_PREPARATION_2026-08-28.html`) : 3 écrans nouveaux (poste, chiffres, intro) + 3 écrans existants (génération/passage IA, relecture avant-après, écran de fin).

### Règle 2bis : AVANT toute maquette ou proposition, tracer le parcours réel COMPLET - écran d'avant, écran d'après, pas seulement le morceau qu'on change

**Rencontré le 2026-08-28, chantier Carte 3 (écran de préparation), signalé fermement par Denis - lui a "pourri l'été".** On a conçu et validé une maquette pour un nouvel écran "poste visé" avant la génération IA. Ce qui n'a PAS été fait : lire tout le parcours Carte 3 existant, écran par écran, fonction par fonction. Résultat découvert seulement au test réel : il existait DÉJÀ un panneau "Candidature" riche (`bilanOuvrirFenetreCandidature`) qui collecte la même information (métier visé, offre, entreprise), et il tournait **APRÈS** la génération (étape "completude", Famille 2) au lieu d'avant. Le nouvel écran faisait donc doublon avec un écran mal placé - incohérence majeure, maquette + corrections en partie inutiles, crédit consommé pour rien, et une vraie détresse de Denis ("j'ai envie de gerber", "il m'a pourri la vie").

**Règle** : avant de proposer une solution, avant de lancer une maquette, avant de consommer du crédit sur des allers-retours :
1. **Dérouler le parcours réel de bout en bout** dans le code : quel écran/fenêtre vient AVANT le point qu'on touche, lequel vient APRÈS, et par quelle transition (quelle fonction, quel `ecran = '...'`, quel bouton).
2. **Lister ce qui existe déjà** qui touche à la même donnée ou au même besoin : `grep` le nom du champ (`dossier.metierCible`...), le nom des fonctions candidates, les fenêtres qui s'ouvrent. Une information demandée à un endroit est souvent déjà demandée ailleurs.
3. **Vérifier le TIMING** : l'info est-elle collectée au bon moment du parcours ? (Ici : le contexte de candidature devait être AVANT le 2e prompt, il était après.)
4. Seulement ensuite, concevoir - en disant explicitement à Denis "voici tout le parcours actuel, voici ce qui existe déjà, voici ce que je propose de changer et pourquoi".

Ne jamais traiter un écran comme une bulle isolée. Un module aussi accumulé que le Bilan (RC-01 à RC-10, Vague 1/2/3, briques 1-5, 3 modes de correction, Assistance à 6 écrans) rend cette discipline **obligatoire** : personne, pas même Denis qui l'a conçu, ne tient tout le parcours en tête sans le re-tracer.

### Règle 3 : travailler par bloc de corrections, jamais réagir à chaud sur chaque remarque isolée

Quand Denis donne une remarque pendant une tâche en cours : si l'opération en cours est presque terminée et que la finir coûte MOINS cher (temps/tokens) que de s'interrompre, la finir, puis appliquer toutes les corrections accumulées d'un coup - sauf si Denis dit explicitement "stop, ce n'est pas la bonne direction" (interruption immédiate dans ce cas précis, toujours prioritaire). Si finir coûte PLUS cher que de s'interrompre tout de suite, le dire explicitement à Denis plutôt que de continuer par défaut sans le signaler. Le but explicite de Denis : passer moins de temps à corriger, plus de temps à obtenir du code qui avance réellement.

### Règle 4 : signaler chaque reprise après une compression de conversation, honnêtement, sans prétendre pouvoir l'anticiper

Demande de Denis le 2026-08-26 : il veut un avertissement quand une conversation a été comprimée ("compactée"/résumée automatiquement par manque de contexte disponible) plusieurs fois, au point que le fil devient flou ou dispersé - pour pouvoir décider d'ouvrir une fenêtre neuve au bon moment plutôt que de s'en apercevoir trop tard.

**Limite réelle, à ne jamais maquiller** : l'assistant ne peut PAS prévenir AVANT une compression - c'est l'application qui la déclenche seule, selon le remplissage du contexte, sans signal transmis à l'avance. Ne jamais laisser croire le contraire.

**Ce qui est réellement possible** : l'assistant reçoit toujours un résumé explicite au moment où une conversation reprend après une compression (marqueur système visible, présent par exemple en tout début de cette session-ci). **Règle** : à chaque reprise de ce type, le signaler explicitement à Denis et donner un avis honnête sur la solidité de ce résumé (des détails semblent-ils déjà perdus ou flous ?) - pour que Denis puisse juger, avec ce signal répété au fil de l'eau si ça se reproduit plusieurs fois dans la même fenêtre, s'il vaut mieux continuer ici ou ouvrir une fenêtre neuve à ce moment précis.

### Règle 5 : toujours vérifier avec la toute DERNIÈRE version du code, jamais un onglet/état dont la fraîcheur n'est pas garantie

Demande de Denis le 2026-08-26, contrôle qualité final du module Repères : Denis doit pouvoir reproduire de son côté exactement ce que l'assistant montre comme preuve - un test fait avec du code périmé (ancien onglet non rechargé, cache navigateur, état JS laissé par un test précédent) donnerait un résultat different du sien, source de confusion et de temps perdu à comprendre un écart qui n'existe pas réellement.

**Règle** : avant toute vérification dont le résultat sera montré à Denis (capture d'écran, description d'un comportement), recharger réellement la page (navigation forcée, jamais réutiliser un onglet resté ouvert depuis plusieurs échanges) pour garantir que le code testé est bien le tout dernier écrit - jamais supposer qu'un onglet déjà ouvert reflète encore l'état actuel du code. En cas de doute sur la cause d'un résultat inattendu (code périmé vs vraie régression vs erreur dans les données de test utilisées pour la vérification elle-même), le dire explicitement et honnêtement plutôt que de conclure trop vite dans un sens ou dans l'autre.

### Règle 6 : dans une longue conversation avec beaucoup de décisions accumulées, tenir une liste explicite des engagements pris - jamais compter sur la seule mémoire du fil

Rencontré le 2026-08-26 (chantier "rapport en accordéons", module Regard extérieur/Repères). Une question systématique ("êtes-vous actuellement accompagné(e), par quelle structure, quel statut ?") a été proposée par l'assistant, validée explicitement par Denis ("OK"), puis jamais codée : la conversation est repartie sur un autre sujet arrivé entre-temps (le regroupement des Repères par catégorie), et l'engagement s'est perdu sans qu'aucun des deux ne s'en aperçoive - jusqu'à ce que Denis le remarque lui-même en testant en réel ("je n'ai jamais vu la fenêtre de questions").

**Cause réelle, sans minimiser** : sur une conversation de cette longueur, avec de nombreuses décisions prises au fil de l'eau (souvent au milieu d'un message plus long portant sur un tout autre sujet), l'assistant n'a tenu aucune liste explicite et visible des engagements de code pris. Chaque nouvelle demande a été traitée dans l'instant, sans repasser systématiquement sur les engagements plus anciens avant de déclarer un lot de travail "terminé". Ce n'était pas un refus ou un évitement délibéré d'une tâche jugée plus coûteuse (celle-ci touchait effectivement plus de fonctions que les autres) - mais ce risque existe tant que rien n'est fait pour s'en prémunir activement.

**Règle** : dès qu'une conversation accumule plusieurs engagements de code distincts (au-delà de 2-3), les reformuler explicitement en liste avant toute grosse passe d'implémentation, et repasser sur cette liste avant de déclarer un lot "terminé" - jamais se fier à la seule relecture mentale du fil, aussi long soit-il. Si Denis doit demander "est-ce qu'il y a des choses que tu as oubliées ?", c'est que ce réflexe n'a pas été appliqué à temps : le but est qu'il n'ait normalement plus jamais besoin de poser la question lui-même.

### Règle 7 : un audit détaillé ou une maquette longuement travaillée s'applique À LA LETTRE, jamais avec des libertés silencieuses

Rencontré le 2026-08-26 : la barre d'onglets fixe de la maquette "Rapport Cohérent" (plusieurs heures de travail commun, validée explicitement) a été implémentée avec un raccourci non annoncé clairement lors du codage réel (sections empilées sans onglets, plutôt que la vraie barre fixe de la maquette) - découvert seulement quand Denis l'a testée en réel, alors que l'assistant avait déclaré le travail "terminé et testé" juste avant.

**Règle, donnée explicitement par Denis, à respecter sans exception** : quand Denis fournit un audit détaillé d'erreurs/incohérences, ou qu'une maquette a été travaillée longuement (plusieurs heures), l'appliquer À LA LETTRE - aucun écart pris de sa propre initiative, même pour "gagner du temps" ou "simplifier". Si un écart semble apporter une réelle amélioration, ne JAMAIS l'appliquer silencieusement : le proposer explicitement à Denis, avec le pourquoi et le bénéfice concret attendu, et attendre sa décision avant de coder quoi que ce soit de différent de ce qui a été validé. Un raccourci non annoncé, même modeste, coûte plus cher en confiance et en temps de re-test qu'il n'en fait gagner.

### Règle 8 : ne jamais déclarer "implémenté et testé" sans avoir vérifié le VRAI chemin qu'emprunte la personne, pas seulement la fonction en isolation

Rencontré le 2026-08-26, même chantier ("rapport en accordéons") : la question systématique d'accompagnement a été codée et déclarée "implémentée et testée" après un test direct de `_regardExterieurConstruireQuestionsAPlat()` en console - correct en lui-même, mais ce test contournait un garde-fou plus en amont (`_regardExterieurLancerApprofondir()`) qui, lui, arrêtait tout AVANT d'atteindre cette fonction dès que les 4 catégories étaient vides côté IA - exactement le cas réel de Denis. Un deuxième passage de vérification a trouvé ce garde-fou, puis un troisième a trouvé la même incohérence sur le bouton "Aller plus loin" de la fenêtre "Voir mon analyse" (caché dans les mêmes conditions, jamais aligné avec la carte de "Mes rapports"). Trois bugs liés, trouvés seulement parce que Denis a explicitement redemandé "est-ce qu'il y a d'autres oublis ?" au lieu d'accepter la première réponse.

Denis l'a formulé sans détour : une déclaration "implémenté et testé" qui s'avère fausse à l'usage a le même effet qu'un mensonge, qu'elle soit intentionnelle ou non - la confiance et le temps perdus sont réels dans les deux cas.

**Règle** : avant de déclarer une fonctionnalité "implémentée et testée", tester le VRAI chemin qu'emprunte réellement la personne depuis le VRAI point d'entrée (le bouton ou le geste qu'elle utilise), jamais seulement la fonction la plus profonde en isolation - une fonction interne correcte ne prouve rien si un garde-fou plus en amont empêche de l'atteindre. Tracer explicitement toute la chaîne d'appels entre le geste de la personne et la fonction testée avant d'affirmer que le chemin complet fonctionne. En cas de doute sur l'exhaustivité de cette chaîne, le dire plutôt que de déclarer un succès qui ne serait vrai qu'en partie.

### Règle 10 : avant de déclarer un module "fini", une relecture "œil neuf" en 3 angles

Origine (2026-08-27) : en 2026-08-22, Denis avait demandé un "audit UX designer senior" complet du module Bilan. Cet audit précis n'a jamais été mené et, le module ayant beaucoup évolué depuis (RC-07, RC-08, stabilisation en 15 points, Assistance à la finalisation), sa cible d'origine n'existe plus. Mais la démarche, elle, reste utile et générale : ce qui est jeté, c'est le périmètre "Bilan 2026-08-22", pas la méthode.

**Règle** : avant de considérer un module réellement terminé (pas juste "les fonctions marchent"), faire une passe de relecture avec un regard neuf, en cherchant explicitement 3 types de défauts :
1. **Hypothèses obsolètes** : un écran affirme encore quelque chose qui n'est plus vrai (souvent un texte qui promet moins que ce que l'app fait maintenant, ou l'inverse - voir aussi section 9.4).
2. **Ruptures de parcours** : un endroit où la personne se retrouve coincée, sans retour possible, ou dans un cul-de-sac (voir section 2 sur "Retour").
3. **Incohérences entre modes/écrans voisins** : deux façons de faire la même chose qui ne se ressemblent pas (couleurs, intitulés de boutons, ordre des étapes), construites à des moments différents (voir sections 1 et 9.15).

Cette passe produit une liste, pas du code - elle est peu coûteuse en budget mais peut révéler de nouvelles tâches, donc à faire à un moment où Denis a la place de traiter ce qu'elle remonte, jamais en fin de quota.

### Règle 11 : une maquette de REFONTE doit être visiblement meilleure, jamais une photocopie annotée de l'existant

**Rencontré le 2026-08-29/30, chantier « consolidation du Bilan ».** En voulant garantir « zéro régression », l'assistant a reproduit l'écran actuel du Bilan quasi à l'identique (mêmes blocs toujours visibles, mêmes couleurs héritées, notes « inchangé » partout). Denis a dû le redire deux fois : *« le but n'est pas de copier ce que j'ai - si c'est pour refaire ce que j'ai, autant garder l'écran actuel »*.

**Distinction à tenir :**
- **Zéro régression** s'applique aux **fonctions** et aux **choix offerts à la personne** (aucune option perdue, aucun bouton retiré sans décision écrite, aucun bouton laissé non câblé, aucune donnée redemandée, aucun prompt appauvri). Ça, c'est intangible. **Précision de Denis (2026-08-30)** : quand il dit « zéro régression », il ne parle **jamais** de régression visuelle (déjà actée par la maquette) - il parle de ne pas perdre de fonctions, de ne pas oublier un bouton / une fonction / une info de prompt, de ne pas laisser un contrôle qui « ne pense à rien ». Méthode + checklist complète dans `docs/TRAVAILLER_AVEC_DENIS.md`, section « Ce que "zéro régression" veut dire ».
- Ça **ne s'applique PAS** au visuel ni à l'interaction. Une refonte doit **améliorer** : charge cognitive plus basse, cohérence avec les autres modules, langage visuel unifié (jetons de couleur, mêmes composants), moins d'écrans. Une maquette de refonte qui ressemble à l'existant a raté son but.

**Méthode de décision demandée par Denis (2026-08-30), à appliquer à toute refonte visuelle :** noter l'existant **sur 20** (charge cognitive, cohérence interne, cohérence inter-modules, clarté du parcours, friction/écrans, compréhension du contenu), noter la proposition **sur 20** sur les mêmes critères. **La refonte doit dépasser l'existant, cible ≥ 18/20.** En dessous, ajuster avant de coder.

**Corollaire** : les notes de comparaison / la justification (« comme dans le code actuel », « décision Denis du … ») vivent dans une **vue de comparaison dédiée** ou un bandeau à part - **jamais** dispersées en italique à l'intérieur de l'écran proposé, qui doit se lire comme un écran fini, pas comme un document de travail annoté.

### Règle 12 : tout choix présenté à Denis vient avec une recommandation ET les bénéfices / risques de CHAQUE option

**Demande explicite de Denis (2026-08-30), à appliquer à toute la méthode de travail.** Chaque fois que l'assistant présente des choix à Denis - `AskUserQuestion`, un tableau d'options, des alternatives en prose - il doit fournir, **sans que Denis ait à le redemander** :

1. **Une recommandation claire** : quelle option est la meilleure / l'optimale, en **une phrase de pourquoi** + **ce que ça apporte concrètement** + **son risque**.
2. **Pour CHAQUE autre option aussi** : ses bénéfices ET ses risques, pas seulement pour celle qu'on recommande.

**But, mot de Denis** : « que je puisse comprendre par moi-même, et aussi avoir une recommandation qui me permettra de voir des dimensions ou des détails qui échappent à mon interprétation et à ma lecture d'ensemble ». La recommandation n'est pas là pour décider à sa place, mais pour **révéler ce qu'il ne voit pas** (dépendances, effets de bord, dette technique, coût de re-test, cohérence inter-modules).

Format : dans `AskUserQuestion`, le champ `description` de chaque option porte son bénéfice + son risque ; l'option recommandée est **en premier** et marquée « (Recommandé) ». En prose, un mini-tableau ou une ligne « bénéfice / risque » par option, puis « Ma recommandation : X, parce que… ». Jamais une liste d'options nues.

### Règle 13 : une donnée / un composant partagé = UNE source de vérité, jamais une copie par contexte

**Demande explicite de Denis (2026-08-30), pendant la consolidation du Bilan.** Constat : pour une seule donnée (le contexte de candidature), il existait **~5 implémentations séparées**, chacune avec sa propre version de la vérité - modifier l'une risquait de casser les autres. Cette architecture rend toute refonte massive et dangereuse.

**À appliquer à TOUT module - création comme refonte :**

1. **Avant de coder un écran / un champ / un composant : chercher s'il existe déjà.** `grep` le nom du champ (`dossier.xxx`), les fonctions candidates, les écrans qui ouvrent la même chose. S'il existe → **réutiliser**, jamais recopier. (Prolonge la Règle 2bis : tracer le parcours réel sert aussi à repérer ce qui existe déjà.)
2. **Un composant qui sert plusieurs contextes se paramètre (`config`), il ne se duplique pas.** Patron : `htmlChoixAssistantBilanCorps(config)` (bloc 2.2).
3. **Toute duplication qui subsiste est une dette listée**, résorbée une par une avec maquette + plan, jamais à chaud, jamais en fin de session.

**Outil** : `docs/BRIQUES_COMMUNES.md` - registre des composants transverses (source unique + consommateurs + dette). **4e fichier à ouvrir** avant tout nouveau module / toute refonte (avec ce fichier, `TACHES_VALIDEES.md`, `IDEES_A_RECLASSER.md`). Le registre se met à jour **dans le même commit** que le composant, sinon il devient une photo périmée (cf. 9.23).

**Corollaire revue** : la Règle 10 (relecture « œil neuf » avant de déclarer un module fini) inclut désormais un 4e angle - **incohérences / duplications entre MODULES** (pas seulement entre écrans voisins) : ce module a-t-il réinventé un composant qui existe ailleurs ?
